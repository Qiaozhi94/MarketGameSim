## 2. `verify.py` 新增的 KPI-006 校验：部分真实修复 + 校验强度不足的实测反例

### 2.1 真实修复的部分

- `_rebuild` 新增处理 `MARGIN_CALL` 里的 `WRITE_OFF_POSTING`，累加 `risk_pnl` 并应用到
  `wallet_units`（原 §1.8 子项之一，确认修复）；
- `_check_c2` 守恒等式新增 `risk_pnl` 项（确认修复）。

### 2.2 `_check_kpi006` 校验强度不足——已实测构造出两个反例

新增函数只做"存在性"检查：任意一笔 AGENT/LIQUIDATION 订单链接正确即判定该分支"通过"，不是
逐笔核对。**反例 1**（10 笔 `origin=AGENT` 订单，1 笔 `decision_event_id` 正确，其余 9 笔指向
不存在的事件 id）：
```
RESULT: {'success': True, ..., 'kpi006_agent_covered': True, ...}
```
9/10 因果链断裂，仍判定通过。**反例 2**（更严重：10 笔订单全部指向不存在的
`AGENT_DECIDE`，且日志里压根没有任何 `AGENT_DECIDE` 事件）：
```
RESULT: {'success': True, ...}
```
因为判定条件是 `has_agent_order and decision_ids and not agent_linked`，`decision_ids` 为
空集时整个检查直接跳过，比"至少一笔正确即放行"更弱。

此外确认：只核对 `decision_event_id → AGENT_DECIDE.event_id` 一跳，不核对后续
`observation_event_id → AGENT_OBSERVE`/`information_set`/`market_data_event_id`（AGENT
分支）或 `risk_mark_event_id`/`chain_id`/`chain_depth`（LIQUIDATION 分支）；不校验
`MARGIN_CALL` 本身字段（`verdict` 取值域、三种 chain 归属规则、`liquidation_generation_after`
换代规则）；KPI-009（PnL 桥接残差）仍未接入。`decision_event_id` 本身也不受 `_rebuild` 的
悬空引用检测约束（该检测只查 `caused_by_event_id`），上述两个反例的"野指针"不会被其他环节
拦下。
