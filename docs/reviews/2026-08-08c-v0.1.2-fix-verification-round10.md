## 0. 结论先行

本轮修复了第九轮报告 §7 列出的 8 项建议中的 8 项（全部完成，无遗留）。全量
`pytest -q` 865 passed（第九轮末尾为 831 passed，净增 34 个新测试，全部为本轮
新增的回归测试，无一个是"事后追认"的桩测试）；`ruff check .`、
`ruff format --check .` 全绿。每项修复都用故障注入方式验证了配套测试确实能捕获
对应的回归（临时还原旧代码 → 确认新测试失败 → 改回修复 → 确认测试通过），过程中
未留下任何调试代码残留（每次故障注入后都核对 `git diff`/直接读取文件确认已还原）。

**修复过程中发现两个第九轮未预见到的深层问题**：

1. `bridge_trade` 的 MULT 缺口比第九轮报告描述的更严重——不只是"忘记乘 MULT"，
   还完全没有把 `entry_notional_delta_units` 和仓位重估计入 `equity_delta`，导致
   即使补上 MULT 缩放，只要交易发生前账户已持有仓位（`pos_before≠0`）且估值锚价
   在本笔成交内发生变化，残差依然非零（实测 80,000,000 cash units）。已根据
   `tests/unit/ledger/test_acceptance_vectors.py::_replay_check` 的独立验证公式
   重新推导并修复。
2. §2.18 的预撮合手续费估算真正接入 `matching.py` 后，第一次全量测试跑出
   **5 个真实断言失败**（`TestCase2CrossPriceHandoff`）——不是我的修复引入了新
   bug，而是 `compute_reserved_with_prematch`（第4轮写下、九轮未接线过、从未被
   验收向量验证过）自身的 `reservation_mark` 设计有缺陷：把候选订单自己的限价
   混入保证金计算的估值锚价，与账户合同 §2.1"开仓不扣名义本金"的杠杆语义矛盾。
   已重新设计该函数，保证金部分固定使用 `risk_mark_ticks`（与
   `compute_reserved_after` 一致），只有手续费估算部分才按订单实际状态两段拆分。

## 1. 已修复清单（对照第九轮报告 §7 的建议顺序）

### 1.1 `test_verify_liquidation.py` 补齐多账户同批场景（建议①）

新增 `test_real_liquidation_log_multi_account_same_batch_passes_verify`：构造 A、B
两个账户在**同一笔风控扫描**中同时触发 `PENDING_LIQUIDATION`，验证
`_run_post_batch_risk_check` 的 `mc_base_index + mc_idx` 索引对齐在批量场景下依然
正确（每个账户的 LIQUIDATION 订单的 `decision_event_id` 精确指向自己的
`MARGIN_CALL`，不会串号）。故障注入（改回 `mc.caused_by_event_id`）后两个测试
（含原有单账户测试）均按预期失败，确认测试有效。

### 1.2 `bridge_trade` MULT 精度缺口——从根源修复，而非仅用 xfail 锁定

原计划是补 `xfail(strict=True)` 锁定已知缺口，但由于已经定位到独立验证公式
（`_replay_check`），改为直接修复 `metrics/bridge.py::bridge_trade`：

* 补上 `mult`/`mult_half` 缩放（消除量纲不一致）；
* `equity_delta` 从"仅 `wallet_delta_units`"改为完整的估值权益增量
  `wallet_delta + position_after×va×mult_half − position_before×vb×mult_half
  − entry_notional_delta`，与 `_replay_check` 的公式代数等价。

新增 `tests/unit/metrics/test_bridge.py`（3 个用例：开仓+手续费残差为0、持仓中
估值锚价移动+平仓残差为0、故意破坏 `entry_notional_delta_units` 后残差必须非0），
并把 `experiment/runner.py::_verify_bridge_residuals` 从 `warnings.warn` 改回硬
`assert`（因为精度缺口已修复，不再需要用警告绕过）。

### 1.3 §2.15 做市商维持保证金分支补齐正反测试（建议③）

### 1.4 KPI-009 接入 `verify.py` 独立验证器（建议④）

### 1.9 §1.5 剩余部分：Dirichlet 权重合成接入生产路径

`agent/handler.py::_compute_belief_signal` 此前硬编码 `weights = [Decimal("0.2")]*5`。
新增 `_belief_weights()`：按 代理策略 §4.2/§10.3.2 的规范，在决策序号 0（建仓期）
用 `dirichlet_draw(alpha=[1.0,1.0,0.8,0.8,1.5], ...)` 为每个代理抽取一次并缓存在
`world["agent_belief_weights"]`，此后同一代理复用同一权重（"运行开始时抽取后固定
不变"）。新增 `tests/unit/agent/test_handler.py`（5 个用例）：直接核对
代理策略 §10.3.4 黄金向量、确认权重不再是均匀 `[0.2]*5`、不同代理权重不同、同一
代理跨调用权重不变（缓存生效）、端到端核对 `_compute_belief_signal` 的输出与
"黄金权重向量 + 独立计算的五个因子"手工组合结果逐位相同。

### 1.10 §2.18 预撮合两段式手续费估算接入 `matching.py`

`book/matching.py` 新增 `_pre_match()`：非破坏性地沿用 `Book.bid_levels()`/
`ask_levels()` 走一遍对手盘价位（复用 `_crosses` 判据，不改动真实撮合循环），
拆分候选订单"立即成交部分"（按逐档真实 maker 价计息）与"入簿残余部分"。
`_populate_r0_defaults` 从"把整张订单当假想挂单，按订单自己限价估手续费"改为调用
`compute_reserved_with_prematch(..., pre_match=_pre_match(...))`。

修复过程中发现 `compute_reserved_with_prematch`（第4轮写下但从未接线/从未跑过
验收向量）自身有一个此前没有暴露的 bug：保证金部分（`margin_part`）的估值锚价
被设计成"取 `risk_mark` 与所有挂单价的较大值"，接入后立刻让
`acceptance-vectors.md` 案例2（三代理跨价换手）的 5 个测试失败——因为该案例里
C 账户的钱包只够按*当前* `risk_mark`（100）覆盖仓位，账户合同 §2.1"开仓不扣名义
本金"的杠杆语义要求准入检查不应该按订单自己的限价（110）估算保证金。已重新设计
该函数：`margin_part` 固定只用 `risk_mark_ticks`（与 `compute_reserved_after`
完全一致），只有手续费部分才做两段式拆分。

新增 `tests/unit/book/test_prematch.py`（7 个用例，覆盖空簿全挂单、单档全成交、
多档成交用逐档真实价而非订单自己限价、BUY/SELL 两个方向的"老实现低估手续费"
现象、限价止步于某档、无穿档、以及端到端走 `match_order` 核对
`reserved_delta_units`）与 `tests/unit/ledger/test_reserved.py` 新增
`TestComputeReservedWithPrematch`（5 个用例，含专门锁定"margin_part 不应该被
订单自己的限价影响"这一具体回归的用例）。均已用故障注入验证（临时改回旧公式，
确认测试失败）。
