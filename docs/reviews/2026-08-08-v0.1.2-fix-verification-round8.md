## 4. 新发现：§2.8/KPI-009 验证强度降级（assert → warning）

`experiment/runner.py::_verify_bridge_residuals`：
```python
if result["residual"] != 0:
    warnings.warn(f"PnL bridge residual {result['residual']} != 0 for {e.get('trade_id')}",
                   stacklevel=2)
```
docstring 写着"See docs/reviews/2026-08-07-v0.1.2-fix-verification-round7.md §3.1"，
但第七轮报告 §3.1 原文记录的修复方式明确是硬 `assert result["residual"] == 0`
（两路并行复核独立确认这一点，包括直接读取 round7 文档原文核对）。当前代码把它
降级成了非致命警告——**残差非零现在不会再让任何测试或运行失败**，这是对已确认
修复项的一次隐性削弱，且没有 git 记录可查具体发生在何时（`experiment/` 目录整体
是未提交状态）。

**含义**：KPI-009（PnL 桥接残差逐事件恒为 0）在生产路径上的实际约束力被削弱，
E7 明文要求的"KPI-009 成立"现在更接近"不报错但可能悄悄不成立"，而不是"验证到位"。

## 8. 建议

1. **§1.11 需要补上集成测试**——用真实清算流程产出的日志（含多账户同批场景）
   跑 `verify_log`，永久锁定"真实清算日志必须通过独立验证器"这条底线，这是
   本轮唯一被反复提及但仍未落实的建议。
2. **`_verify_bridge_residuals` 的 assert→warning 降级需要复核动机**——如果是
   因为发现某些合法场景残差本来就不总是精确为 0（比如浮点/舍入边界），应该在
   docstring 里如实说明并给出具体场景，而不是引用一份记录着"应该用 assert"的
   报告却做了相反的事；如果没有正当理由，应该改回 assert 或至少改为
   `pytest.warns` 能捕获、失败会被测试感知的形式。
3. **§2.2/§2.5、§1.11、§2.15 三处本轮确认的行为需要补齐 `tests/unit/metrics/`
   与相应的集成测试**——目前这些结论全部依赖复核者的临时脚本，仓库测试套件
   没有任何保护。
4. 其余建议维持第七轮 §7 的优先顺序（KPI-009 接入 `verify.py`、链条深度加深、
   §1.7/§2.7 配对与统计口径、Case 8/9 测试等）。
