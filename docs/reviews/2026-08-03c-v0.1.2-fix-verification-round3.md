## 0. 结论先行

**"所有问题都修复完成"第三次不成立。** 但这一轮确实有实质性的、可验证的真实进展：测试总数从
814（第一轮）→ 814（第二轮）→ **820（本轮，+6）**，`OB-8`/`OB-9b` 首次有了对照黄金向量精确整数
的可执行测试，`maint_bp` 未接线、`master_seed` 硬编码、拒绝分支 `reserved_delta_units` 未归零
这三个此前反复被指出的问题这次都用正/负对照实验确认为**真修复**。

**但本轮复核过程中，账本层复核用真实撮合引擎复现了一个新的、更严重的问题**：强平订单的
"世代校验"（`liquidation_generation` / `LIQUIDATION_STALE`）机制在生产代码里完全不存在——
不是没测试，是压根没有这段校验逻辑。复核者构造了账户合同 T202b 明确给出的验收场景（账户跌破
维持保证金→调度强平单→延迟窗口内价格反弹、账户恢复健康→过期的强平单仍然到达），用真实的
`match_order` 撮合引擎跑了一遍，**这张本该被拒绝的陈旧强平单被正常接受并成交，把已经恢复健康
（`margin_ratio_bp=1000`）的账户强制砍掉了 287,235 单位仓位，产生 2,872,350,000 单位的实现
亏损**——这正是账户合同原文警告的"不换代会让新旧两张单都通过验证，账户被过量强平"。

同时发现了一个比第二轮报告中 `maint_bp` 更下游的新短路点：`leverage_tier` 从未被接入订单
准入闸口实际使用的 `agent_initial_bp`，导致即使 `maint_bp` 这根线通了，`experiment/runner.py`
里"由代理自主决策驱动"的完整实验管线，目前**在数学上无法产生真正的杠杆强平**（所有仓位准入
时都按 1x/100% 保证金计算，而全额抵押仓位不会跌破维持保证金）。

**`verify.py` 是本轮最值得单独强调的一点**：连续三轮声称"全部修复"，该文件从第一轮报告写成
之前到现在，**`git diff` 逐字节零差异**——三轮里没有任何一次改动。第一轮报告 §1.8（6 个子项）
和 §4.1–§4.5（5 项）全部原封未动。

## 1. 本轮新发现的问题（比前两轮都更严重）

### 1.1【新发现，最高优先级】`LIQUIDATION_STALE` 世代校验完全未实现，已实测复现真实"过量强平"

- **位置**：应存在而不存在的校验逻辑，缺口在 `src/market_game_sim/book/matching.py`
  （处理 `origin=LIQUIDATION` 的 `ORDER_ARRIVAL` 的路径）与
  `src/market_game_sim/hook/crypto_perp.py:27-34`（`validate_order` 仍硬编码
  `return True, None`，自 0.1.1 起未变）。
- **证据**：`grep -rn "LIQUIDATION_STALE" src/ tests/` 仅在
  `schema/event_fields.json:587`（枚举值定义本身）命中。`matching.py:486` 只是
  `event.setdefault("liquidation_generation", None)`，`matching.py:730` 只是在新调度强平单
  时把账户当时的世代号"贴标签"写上去，**全仓库没有任何代码在强平单到达时把它携带的世代号
  与账户当前的世代号做比较**。`risk.py` 里世代号本身的递增逻辑是对的（进入 pending +1、数量
  重算 +1、恢复 +1），缺的只是"新到订单要不要被接纳"这一环。
- **实测复现**（用真实 `match_order` 撮合引擎，不是构造断言猜测）：
  1. 账户 A 于 mark=94 跌破维持保证金（`margin_ratio=425bp<500bp`），产生
     `MARGIN_CALL verdict=PENDING_LIQUIDATION`，调度强平单，携带
     `liquidation_generation=1`；
  2. 强平单还在 `liquidation_latency_ns` 延迟队列里、尚未到达时，价格回升到 100，A 恢复
     `ACTIVE`（`MARGIN_CALL verdict=OK`，世代号变为 `2`，`margin_ratio_bp=1000`，远高于
     维持线）；
  3. 那张携带**过期世代号 `gen=1`**的强平单随后到达：
     ```
     {'event_type': 'ORDER_ARRIVAL', 'agent_id': 'A', 'origin': 'LIQUIDATION',
      'liquidation_generation': 1, 'accepted': True, 'reject_reason': None, ...}
     {'event_type': 'TRADE_SETTLE', 'taker_agent_id': 'A',
      'quantity_units': 287235, 'price_ticks': 9990,
      'realized_pnl_delta_units': -2872350000, 'position_after_units': 212765, ...}
     ```
     **该订单应当被拒绝（`accepted=false, reject_reason=LIQUIDATION_STALE`），实际却被当作
     普通市价单正常撮合成交**，把已经恢复健康的账户强制砍掉 287,235 单位仓位，产生
     2,872,350,000 单位的实现亏损。
- **违反**：账户合同 T202b 明确给出的两条验收用例（①延迟窗口内恢复后强平单必须被拒；
  ②pending 期间连续两次数量变化、三张单乱序到达时只有最新代次通过）——这两条用例目前在
  生产代码里都无法通过，因为压根没有这段校验逻辑，而不是逻辑有 bug。
- **含义**：这不是理论风险，是用当前代码库里已经存在的真实撮合引擎实测复现的资金损失级
  场景，应作为下一轮修复的最高优先级。

### 1.2【新发现】`leverage_tier` 从未接入订单准入闸口，杠杆强平在代理驱动的完整实验管线中实际无法发生

- **位置**：`src/market_game_sim/book/matching.py:265-266`
  （`_initial_bp` 读取 `world.get("agent_initial_bp", {}).get(agent_id,
  _INITIAL_MARGIN_BP_011)`，默认值 `10000` = 1x/100% 保证金）；
  `src/market_game_sim/experiment/runner.py`（`run_one` 的 `world` 构造从未写入
  `agent_initial_bp` 这个 key）。
- **证据**：`grep -rn "agent_initial_bp" src/` 全仓库只有 `matching.py` 里的
  `setdefault`/`.get()` 两处，`runner.py` 逐行核对没有这一项。`AgentSpec.leverage_tier`
  （`agent/scheduler.py:25`）只被 `strategy.py::order_intent_from_signal` 用来计算"客户端
  自认为该下多大仓位"，真正把关"这笔单子能不能通过"的准入检查（`matching.py:72-91`）永远
  用 1x 计算，与 `leverage_tier` 完全无关。
- **实测**（构造 `leverage_tier=10` 的 agent，同一笔应享受 10 倍杠杆的订单）：
  ```
  不接 agent_initial_bp（现状）：accepted=False, reject_reason=INSUFFICIENT_MARGIN
  手动补上这根线（对照）：       accepted=True,  reject_reason=None
  ```
- **含义**：即使本轮已经把 `maint_bp`/`target_bp` 接通（见 §2.1），`experiment/runner.py`
  作为"agent 自主决策驱动完整实验"的管线，目前仍然事实上无法产生真正意义上的杠杆强平——
  全额抵押仓位在数学上价格下跌时保证金率不降反升，逼近破产点前不会跌破维持线。这是比
  `maint_bp` 更下游的同类"接线断裂"问题，建议一并列入下一轮清单：`run_one` 的 `world`
  构造需要补上
  `"agent_initial_bp": {s.agent_id: initial_margin_bp_for_tier(s.leverage_tier) for s in
  config.agent_specs}`。

## 4. 建议

1. **`LIQUIDATION_STALE` 世代校验是当前最高优先级**——已经证明会导致真实资金损失级的错误，
   且实现思路是明确的（`matching.py` 处理 `origin=LIQUIDATION` 的订单时，比较
   `event["liquidation_generation"]` 与 `world["accounts"][agent_id].liquidation_generation`，
   不等则 `accepted=false, reject_reason="LIQUIDATION_STALE"`，事务只有 r0）。
2. **`agent_initial_bp` 接线**是让 §2.1 已经修好的 `maint_bp` 真正在完整实验管线里发挥作用的
   必要前提，工作量很小（一行 dict comprehension），建议与 §1.1 一起处理，处理后应该用
   `experiment/runner.py::run_one` 跑一次由代理自主决策驱动、不手工构造穿仓账户的完整场景，
   确认真的能产生 `MARGIN_CALL`。
3. **`verify.py` 需要作为独立任务明确排期**，不能继续依附在"这一轮改了什么就顺带看看"的
   模式里——它连续三轮没有被碰过，本身就说明它没有被纳入任何一轮的实际修复范围。
4. **在下一次准备宣布"修复完成"之前，建议先自查一遍这三份复核报告里所有"未修复"的条目，
   逐条确认改动，而不是只处理复核报告点名的"最新发现"**——这三轮呈现的模式是：每轮集中
   解决 2-4 个具体点，但报告里其余大量条目原封不动地跨轮次结转，说明修复过程本身可能是
   逐条应答式的（针对复核报告的具体行动项做），而不是系统性地过一遍全部已知问题清单。
