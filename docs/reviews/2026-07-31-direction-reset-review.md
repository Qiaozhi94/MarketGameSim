## 1. 执行摘要

本次方向重构把项目从「观察异质代理如何形成价格」改为「把交易信念转化为可证伪的条件性命题」。新方向比旧方向拥有更明确的问题、用户价值和实验产出，值得保留。

当前主要风险不是文档数量不足，而是新产品承诺、模型证据能力和 MVP 范围尚未完全匹配：

1. 产品不能验证交易信念在真实市场中的有效性，只能在声明的合成市场模型族中进行反事实压力测试；现有名称和部分措辞容易让目标用户高估结论能力。
2. 方向重构后，第一版同时加入双市场制度、杠杆、强平、连续信念空间、收益归因和回放，实际范围较旧版显著扩大。
3. 若干核心合同尚未闭合，包括制度生命周期事件、强平事件排序、信号到订单的映射、守恒口径、市场验证门槛和 PnL 渠道定义。
4. 旧版已冻结的 `EXP-000` 被删除，而新版基准市场验证协议仍待制定，造成实验成熟度倒退。

建议将产品正式定位为：

> MarketGameSim 是一个可复现的合成市场反事实与压力测试环境，用于把交易信念转化为条件性实验命题，识别其依赖机制、适用区间和反例；它不判断该信念在真实市场中的有效性。

第一版应围绕一个旗舰研究问题形成完整闭环，而不是立即实现通用的双制度实验平台。

## 3. 方向重构评估

### 3.1 值得保留的变化

#### 3.1.1 从平台建设转向问题驱动

旧方向主要回答「异质参与者互动后会发生什么」，容易长期停留在扩充代理与图表。新方向要求每项开发服务于可证伪问题、对照设计和条件性结论，使产品拥有更明确的完成定义。

#### 3.1.2 三层结构基本合理

「市场微观结构地基 → 信念检验 → 可玩模拟器」的依赖顺序正确。市场机制与实验复现没有通过时，不应解释策略收益；人在环数据也不应混入正式研究样本。

#### 3.1.3 结论纪律明显增强

以下约束应继续保留：

- 不从单次路径得出一般结论；
- 输出效应量、置信区间和失效边界；
- 区分角色、能力和行为；
- 防止把预设代理规则重新描述为涌现发现；
- 不把合成市场结论外推为真实交易建议；
- 对资金、信息、速度和执行能力采用单维度配对对照。

### 3.2 需要收紧的产品承诺

当前首要用户被定义为「有实盘经验、希望研究自己信念的交易者」，但模型同时具有以下边界：

- 不存在外生基本价值或新闻通道；
- 使用人工代理和人工制度参数；
- 不做真实数据校准；
- 不允许把结论外推至真实市场；
- 不生成交易信号。

因此系统能够否定的是「信念在某个模型族中的无条件成立」，而不是「信念在真实市场中的成立」。建议在 PRD 摘要、愿景、报告模板和所有用户场景中统一使用以下证据口径：

> 在模型族 M、参与者结构 S、参数区间 R 和随机输入集合 Z 下，信念 B 的目标效应为 X；在条件 C 下失效。该结论仅说明这些机制足以或不足以产生目标结果。

### 3.3 「无外生基本价值」的概念表述需修正

当前文档将「不引入外生基本价值」表述为技术分析第一公理「价格包含一切」的实现。这一推论过强：删除其他信息源，只表示模型选择隔离订单流和价格反馈机制，不表示价格已经包含真实世界的全部有用信息。

建议改为：

> 无外生基本价值是一项实验隔离选择，用于研究订单流和价格反馈是否足以产生目标现象；它不是对真实市场信息效率或技术分析公理的认可。

### 3.4 目标用户与实际工作流不完全匹配

当前用户需要自行完成可证伪提问、对照设计、参数扫描、排除规则和统计解释。这更接近研究者/开发者，而不是一般实盘交易者。

建议近期用户排序为：

1. 首要用户：市场机制研究者和能够编辑配置的开发者；
2. 协作用户：提供信念、审阅机制解释的资深交易者；
3. 远期用户：通过实验向导使用预制模板的普通交易者。

在开发复杂 UI 前，建议先收集 10—20 条真实交易信念，判断其中多少能够被当前信息集、制度和指标表达。

### 3.5 MVP 范围在重构后反而扩大

旧版以加密现货、单制度和市场基础为主；新版第一版同时包含：

- 股票式与加密式制度；
- T+2、熔断、收盘与隔夜；
- 融资、全仓保证金、强制平仓和穿仓；
- 连续信念空间与五类因子；
- 做市商、大资金执行者和订单流预知者；
- 四渠道 PnL 分解；
- 事件回放与远期人在环兼容。

这些功能分别服务于不同研究问题。建议以一个旗舰问题约束第一版，例如：

> 在无外生价值冲击的加密式连续市场中，初始杠杆分布与维持担保比例是否足以产生自我强化的价格崩盘？

相应第一版只保留：一种加密保证金制度、最小代理集合、杠杆/强平、无杠杆对照、市场质量指标和崩盘/连锁指标。股票式制度、T+2、订单流预知和通用收益归因后移。

### 3.6 方向迁移治理不完整

将旧规格从当前有效路径移除可以避免误用，但完全依赖 `git show 41240a2` 不利于发现变更背景。尤其旧版已冻结的 `EXP-000` 含具体假设、扫描、排除标准、统计方法和停止规则；这些内容仍适用于新版的内生锚稳定性验证。

建议新增一份方向迁移记录，至少包含：

- 旧方向为何终止；
- 新方向的可证伪产品假设；
- 哪些旧需求继续生效、被修改或废止；
- 旧实验协议中继续使用的部分；
- 新方向在何种证据下应再次调整或终止。

## 4. P0 阻断问题

### P0-01【已关闭 · 范围收敛至加密式，股票式生命周期事件后移（事件 Schema §1.3）】：事件体系不能承载全部制度生命周期

**现状**：事件类别仅包含订单到达、成交结算、保证金判定、行情发布、代理观察/决策和快照。股票式制度还要求开盘、收盘、熔断、恢复、T+2 到期结算；强平失败还要求重试调度。

**冲突**：

- `MARGIN_CALL(class 1)` 产生 `ORDER_ARRIVAL(class 0)`，发生 class 回退；
- 收盘 `SNAPSHOT(class 5)` 触发 `MARGIN_CALL(class 1)`，同样回退；
- `grace_ns = 0`，但新事件仍必须严格晚于当前事件；
- 文档却称只有 `AGENT_DECIDE → ORDER_ARRIVAL` 会回退 class。

**风险**：不同实现会选择人工增加 1 ns、引入隐藏事件、在钩子中直接改变状态或违反队列单调性，导致哈希、因果链和市场行为不一致。

**建议**：

1. 新增交易所生命周期事件，例如 `SESSION_OPEN`、`SESSION_CLOSE`、`HALT`、`RESUME`、`SETTLEMENT_DUE`；
2. 新增或明确 `LIQUIDATION_RETRY` 的调度语义；
3. 为全部事件转换建立矩阵，逐项证明 `key(child) > key(parent)`；
4. 冻结事件类别前先完成股票式与加密式各一条完整因果链示例。

### P0-02【已关闭 · 由 `docs/contracts/agent-strategy.md` 承接】：信念信号尚未形成可执行的代理策略合同

**现状**：规格定义了五类因子及加权信号，但没有定义信号如何转换为订单。

**缺失项**：

- 因子尺度标准化、截断和缺失值处理；
- 历史不足、尚无成交、单边簿、总成交量为零时的因子值；
- 信号到买卖方向、价格、数量和订单类型的映射；
- 撤单、重报、持仓限制和风险预算；
- EWMA、K 线历史和初始订单簿的启动方式；
- 做市商与普通信念代理共享和不共享的行为部分。

**风险**：上述自由度会直接决定厚尾、波动聚集、因子收益和崩盘频率，实验结论可能只是实现者选择的结果。

**建议**：新增“代理策略合同”，将下列管线写成确定函数：

```text
information_set
  → raw factors
  → normalized factors
  → belief signal
  → desired inventory / risk target
  → order intents
  → admission constraints
```

### P0-03【已关闭 · §15.2 P0-G01】：当前权益守恒式在非零市场净持仓下不成立

**现状**：指标字典要求：

```text
Σ代理权益(t) + 交易所费用(t) + 风险账户(t)
  = Σ代理权益(0)
```

代理权益使用当前 `mark` 计价，而两份基准配置都给全部代理配置了正的初始持仓。若全市场净库存不为零，价格变化会改变这些资产的总市值，因此等式无法保持常数。

**建议方案（三选一）**：

1. 强制封闭市场初始净持仓为零；
2. 引入发行人/资产供给账户，并将其负库存或资产负债纳入守恒；
3. 拆分为现金守恒、库存守恒、费用对账和 mark-to-market PnL 桥接，不再把市值权益声明为常数。

无论选择哪一项，都应补充一组最小会计示例：无手续费成交、正费率、负 maker 费率、融资买入、强平、穿仓和价格变化但无成交。

### P0-04【未关闭 · 后移，0.1.2 T002/T003 为正式实验前置】：市场可信度门槛尚不可执行

**现状**：PRD 列出厚尾、自相关、波动聚集、点差、深度和冲击非线性，但缺少预先冻结的数值门槛和统计判定规则。

**缺失项**：

- 每项指标的检验统计量和通过区间；
- 置信水平或目标估计精度；
- 多重比较处理；
- 最低有效样本数和功效依据；
- 失败/不适用的判定条件；
- 校准数据与验证数据的隔离；
- 哪些特征是特定研究问题的必要门槛。

**建议**：恢复并改写旧 `EXP-000`，形成 M2 正式预注册协议。把“市场像市场”改为“对目标研究问题足够适用”，避免把一组风格化事实误当作通用模型真实性证明。

### P0-05【已关闭】：经济性崩盘被误归为无效样本

**现状**：价格触底、十倍偏离和强平导致订单簿清空均被标记为无效，并排除出统计特征检验。

**风险**：这些恰好是杠杆连锁研究的核心结果。统一排除会使推断条件化于市场幸存，系统性低估尾部风险。

**建议**：区分两类终止：

- **技术无效**：实现异常、日志损坏、未定义领域状态；允许排除；
- **经济终点**：崩盘、穿仓、流动性枯竭、全市场强平；属于有效结果。

报告采用两部分估计：

1. 经济终点发生概率、发生时间和严重度；
2. 条件于未发生终点时的连续市场指标。

### P0-06【已关闭 · 指标字典 §5.2 五项 PnL 桥接】：四渠道 PnL 分解没有数学定义

**现状**：需求要求将 PnL 分为价差收入、冲击成本、择时损益和对手方转移，但指标字典未定义基准价格、归因窗口、渠道互斥性和残差。

**风险**：价差、冲击和择时天然可能重叠；“对手方转移”又可能只是零和对账的另一种表达。不同算法可为同一成交产生不同解释。

**建议**：在指标字典增加正式归因协议，明确：

- 每笔成交的基准中间价；
- 即时与延迟 markout 窗口；
- 手续费、融资成本和穿仓损失的归属；
- 四渠道是否要求互斥并精确加总；
- 残差的定义和允许范围；
- 至少两个手工可验算示例。

若无法得到稳定、互斥的四渠道分解，第一版应降级为成交成本、库存重估、手续费和融资/违约损失四项会计桥接，而不是承诺经济含义更强的归因。

## 5. P1 重要问题

### P1-01【已关闭】：卖空制度跨文档冲突

退化状态合同称 MVP 不允许卖空，而加密基准配置为 `short_selling: allowed`。应分别声明股票式融券、加密保证金空仓和普通现货卖出，并为每种制度冻结准入及保证金口径。

### P1-02【已关闭并后移】：订单流预知定义存在因果自指

“未来 N 个事件内的订单”可能受预知者当前决策影响；尚未被保证金事件生成的强平单更不可能已知。

建议仅允许查看“已经承诺并已进入通信队列、但尚未到达交易所”的订单意图。必须明确预知者不能看到由自身行动改变后才会生成的未来事件。

### P1-03【已关闭】：配对种子不保证配对随机路径

仅按 `agent_id` 派生 RNG 时，处理变量改变代理行为后，随机抽取次数和顺序会分叉。相同种子仍可复现，但不再构成强配对。

建议按以下语义键派生随机数：

```text
(master_seed, agent_id, random_mechanism, decision_index, draw_index)
```

或者预生成实验共同使用的外生噪声证据包。报告应区分“相同种子”与“相同随机冲击路径”。

### P1-04【已关闭】：性能基准未证明覆盖制度特有路径

股票式基准按 100,000 个事件终止，但未声明必须跨越收盘、T+2 或触发熔断检查。若事件在开盘后的数百秒内已耗尽，所谓股票式基准并未覆盖最昂贵、最复杂的路径。

建议增加覆盖断言，例如：

- 至少完成三个交易日；
- 至少发生一次收盘判定和一次 T+2 到期；
- 熔断钩子至少执行固定次数；
- 强平与普通订单路径分别有最低事件数。

性能基准应新增 `run_mode: benchmark`，避免 `research + digest + 不落日志` 的语义冲突。

### P1-05【已关闭】：基准配置不是严格的单变量制度对照

两份配置除制度外还改变最小数量、费率、杠杆档位和杠杆分布。用于性能覆盖可以接受，但不能据此宣称结果差异仅来自制度。

建议区分：

- `BENCH-*`：性能路径覆盖，不承担因果制度对照；
- `EXP-REGIME-*`：研究用制度对照，明确哪些参数属于制度处理包，并给出可比性理由。

### P1-06【未关闭 · 后移，方法论 §10.3 三区分离 + 0.1.2 T004】：市场验证与信念检验可能发生双重使用

如果先调节代理参数使市场呈现厚尾和波动聚集，再使用同一参数区域检验动量/从众信念，结论可能受校准目标诱导。

建议将参数空间拆为：

- 校准区：选择模型可用区域；
- 冻结验证区：检验市场充分性；
- 信念实验区：在预先声明的模型族中测试目标命题。

最终结论应跨替代代理规则或模型族复核。

## 7. 建议的产品与研究架构

建议把仓库概念上拆成四层，每层分别验收：

```text
L1 确定性市场内核
   订单簿、账户、事件调度、制度生命周期、日志
        ↓
L2 模型族
   代理策略合同、信息集、信念分布、风险约束
        ↓
L3 实验协议
   研究问题、处理、共同随机输入、终点、统计方法
        ↓
L4 产品呈现
   条件性结论、证据包、回放、限制声明
```

关键原则是：事件内核正确不等于模型可信，模型满足风格化事实不等于实验识别有效，实验识别有效也不等于可以外推到真实市场。

## 11. 最终建议

本次方向重构不应回退。相比旧版，新版更接近一个能够产出明确研究结果的产品。但建议进行一次“小型二次收敛”：

1. 将“验证真实交易信念”收紧为“在合成市场中压力测试信念与机制”；
2. 用一个旗舰问题和一个制度完成首个端到端实验；
3. 先证明内核、模型和实验三层分别成立，再扩展为通用平台；
4. 恢复旧版实验协议中仍有效的研究资产，而不是从头重新发明；
5. 把本文 P0 项关闭后，再宣布文档层面具备完整开发条件。

若按此顺序推进，项目可以同时保留新版的产品价值和旧版的工程严谨性，并显著降低在实现中重做事件系统、账户模型和代理行为的风险。

### 12.3 当前 P0 阻断项

#### P0-R01【已关闭 · §13.2】：冷启动规则形成永久停滞

代理策略合同同时规定：

- 初始订单簿为空；
- `mark` 未定义时跳过目标仓位决策；
- 两侧订单簿皆空时不下单；
- 做市商报价需要 `mid`。

因此不会出现第一张订单或第一笔成交，与“由 noise 和 book 因子启动市场”的说明矛盾。

**关闭条件**：冻结唯一的启动规则。建议做市商在首笔成交前使用 `initial_price` 作为临时参考价挂出确定性双边报价；首笔成交产生有效 mark 后永久停用该回退。增加“空市场启动至首笔成交”的验收示例。

#### P0-R02【已关闭 · §13.2 转 P0-F01/F02，终结于 §15.2】：杠杆现货与永续合约语义混合

当前制度名为 `crypto_perp_free`，但账本按现金与库存交割；指标示例用负现金表达融资，退化状态又要求现金不得为负；预冻结规则要求冻结全部名义金额，又会阻止缺少全额现金的杠杆买入。

**关闭条件**：编码账户前二选一并形成合同：

1. **杠杆现货**：增加债务字段和借款/偿还分录，定义利息、资产负债担保比例及违约核销；或
2. **线性永续**：使用钱包余额、合约仓位、开仓成本、已实现/未实现 PnL 和初始/维持保证金，不按现货名义金额交换现金与库存。

所选模型须同步制度名、账户字段、守恒式、预冻结、卖空和手工示例。

#### P0-R03【已关闭 · §13.2 主体关闭，余项转 P1-F01】：保证金公式与开仓约束未定义

`margin_used`、`collateral_ratio` 与 `required_quantity_units` 只有字段，没有完整公式；1x 账户的分母退化、初始保证金与维持保证金的区别、多空对称性和部分成交后的重新计算均未定义。当前准入只检查维持线，也没有单独的初始保证金要求。

**关闭条件**：新增保证金与债务合同，至少包含：

- 初始保证金、维持保证金和目标恢复线公式；
- 1x、多头、空头的分母与边界行为；
- 可开数量和 `required_quantity_units` 的整数算法与舍入方向；
- 多头开仓、空头开仓、价格变化、部分强平、恢复目标线五个手工示例。

#### P0-R04【已关闭 · §13.2】：mark 变化与保证金检查的触发链不一致

指标字典以 `mid` 为主要 mark，因此挂单、撤单和全撤重报都可能改变 mark；事件 Schema 却只允许 `MARGIN_CALL.caused_by_event_id` 指向 `TRADE_SETTLE`。报价导致的 mark 变化既无法可靠触发风险扫描，也可能在薄簿中制造“报价触发的强平连锁”。

**关闭条件**：冻结 mark 与风险扫描策略。第一版建议：

- 强平 mark 使用最近成交价，首笔成交前使用 `initial_price`；
- 每次成交更新 mark 后扫描所有有仓账户；
- `MARGIN_CALL` 明确指向导致 mark 变化的事件；
- 报价和撤单本身不得仅凭移动中间价触发强平。

若坚持用 `mid`，则必须在每次簿变更后扫描，并增加抗薄簿操纵或异常报价的 mark 规则。

#### P0-R05【已关闭 · §13.2 转 P0-F03，终结于 §15.2】：穿仓风险账户符号破坏 C1

当前 `negative_equity_units` 是正的穿仓损失，C1 又将交易所风险账户相加。若代理负现金被核销为零，同时风险账户增加正损失，现金总和会增加而不是守恒。

**关闭条件**：二选一：

- 风险账户使用有符号 `exchange_risk_pnl_units`，交易所损失记负数并在 C1 中相加；或
- 风险损失保持正数，但 C1 改为减去该损失。

同时定义穿仓确认前与核销后的两步分录，并修正 `FundingAndDefault` 在代理 PnL 中的时点和符号。

#### P0-R06【已关闭 · §13.2】：强平失败重试没有事件语义

退化状态称部分成交或无对手方时“下一事件重试”，但未定义谁创建该事件、时间如何前进、没有其他市场事件时如何唤醒，以及如何避免强平事件饿死普通代理事件。

**关闭条件**：新增明确的 `LIQUIDATION_RETRY` 调度语义，或规定待强平账户在每次相关行情/订单簿变化后重新评估。必须冻结重试时间、因果外键、优先级、公平性和自然终止条件。

### 12.4 当前 P1 重要项

#### P1-R01【已关闭 · §13.2 转 P1-F02，终结于 §17.2】：策略计算尚未纳入确定性数值合同

策略使用 `ln`、`2^(-1/τ)`、标准正态、激进度乘法和 `round()`，这些计算会改变最终 tick 与数量，却没有冻结中间精度、平局舍入方向、标准正态算法和信号量化规则。

**建议**：把归一化信号量化为固定整数域；明确所有乘除和目标仓位的舍入方向；冻结随机数到标准正态的变换算法。对恰好位于半 tick、半数量单位和信号阈值的案例增加跨进程测试。

#### P1-R02【已关闭 · §13.2】：“初始杠杆分布”与实际配置不符

基准配置给所有同类代理相同初始现金和持仓，分布字段实际抽取的是 `leverage_cap`，不是初始实际杠杆。旗舰问题因此研究的是“可用杠杆上限”，而非声明的“初始杠杆分布”。

**建议**：要么配置真实的初始债务/仓位使实际杠杆达到各档，要么把旗舰问题、A-005、配置注释和报告统一改为“杠杆上限分布及其内生建仓后果”。

#### P1-R03【已关闭 · §13.2】：burn-in 长于最低研究运行

策略合同的冷启动期为 61 根一分钟 K 线，即 3660 秒；指标字典只要求至少 2000 个一秒采样点。运行可能尚未结束 burn-in 就已经满足旧终止条件。

**建议**：研究运行最低长度改为 `burn_in + 至少 2000 个有效分析采样点`，并分别记录总采样数、剔除数和有效数。

#### P1-R04【已关闭 · §14.2 由 P1-F04 承接关闭】：全账户保证金扫描未写入合同

一次成交改变 mark 时，受影响的不只是 maker 和 taker，而是所有持仓账户。若只检查成交双方，连锁强平不会完整发生。

**建议**：第一版明确采用 O(N) 扫描所有有仓账户，保证正确性；性能成为瓶颈后再引入按清算价格排序的风险索引。

#### P1-R05【已关闭 · §13.2】：信息集没有说明如何补齐观察间隔内的成交

回归锚声称按每笔“可见成交”更新，但信息集只列“最近成交”。观察频率不同的代理是否会接收两次观察之间的全部成交，尚不清楚。若只取最后一笔，锚的差异同时混入漏采样效应。

**建议**：明确行情通道是增量事件流还是快照；若为快照，EWMA 应改为全局已完成成交序列的延迟副本，或明确只按观察样本更新并将其作为模型假设。

### 13.3 当前 P0 阻断项

#### P0-F01【已关闭 · §14.2 转 P0-G01，终结于 §15.2】：线性永续的 C1/C2 守恒推导错误

账户合同 §2.3、指标字典 §5 和规格 SC-001 同时声明：

```text
Σ wallet + exchange_fee + exchange_risk = initial Σwallet
Σ position = 0
Σ entry_notional = 0
∴ Σ equity = Σwallet = 常数
```

其中 `Σposition = 0` 对每笔一多一空的永续成交成立，但 `Σentry_notional = 0` 和 `Σwallet = 常数` 在仓位按不同价格换手后不成立。

最小反例：

1. A 从 B 买入 1 手，成交价 100：A 的 `entry_notional=+100`，B 为 `-100`；
2. A 再以 110 卖给新对手 C：A 平仓实现盈利 10，钱包增加 10；
3. 平仓后 A 的开仓成本归零，B 仍为 `-100`，C 为 `+110`；
4. 因而 `Σentry_notional=10`，`Σwallet` 也增加 10；两者的差仍可守恒，但它们各自并不为零或常数。

**关闭条件**：二选一并统一所有合同：

1. 保留逐仓开仓成本法，将全局断言改为包含开仓成本的联合恒等式，例如：

   ```text
   Σ position = 0
   Σ(wallet − entry_notional) + exchange_fee + exchange_risk
       = initial Σwallet
   ```

   最终精确符号应以费用、资金费和核销的完整手算分录证明；或
2. 引入中心化逐日盯市/变动保证金结算，把未实现盈亏在规定时点转入钱包并重置开仓成本，再重新定义钱包守恒。

必须增加“三代理跨价换手”测试，避免只用一对多空且从不更换对手方的示例误证恒等式。

#### P0-F02【已关闭 · §14.2 转 P0-G03，终结于 §15.2】：PnL 桥接仍按旧现货账本推导

指标字典 §5.2 虽已使用永续术语，但仍以 `equity = cash + position × mark` 推导，并在示例中让买入扣除全额现金、以负现金表示融资。这与账户合同规定的“开仓不交换名义本金”和 `equity = wallet + position × mark − entry_notional` 直接冲突。

此外，`FundingAndDefault` 在总公式中被减去，而账户合同又把代理侧违约项规定为负数，存在双重反号风险；“融资利息为 0”也应改为“第一版永续资金费为 0”。

**关闭条件**：

- 以 `wallet`、`position`、`entry_notional` 和风险/报告 mark 重写代数推导；
- 明确 `FundingAndDefault` 到底存储有符号 PnL 贡献还是正的成本，并统一总公式；
- 用永续分录重写全部示例，不得再用买入扣名义本金或负现金融资；
- 至少覆盖同向开仓、部分平仓、跨价完全平仓、反向翻仓、手续费、资金费和穿仓核销；
- 对每个示例同时断言 `Δequity`、五项桥接加总和事件分录重放结果，残差整数精确为 0。

#### P0-F03【已关闭 · §14.2 转 P0-G02，终结于 §15.2】：穿仓核销没有符合 Schema 的事件载体

账户合同 §5 要求穿仓确认和核销分两步，并称核销记录在“同一 `MARGIN_CALL` 事件的账户分录”。但事件 Schema 的 `MARGIN_CALL` 只有判定字段，没有 `postings`、`wallet_delta_units` 或 `risk_pnl_delta_units`；风险账户字段只出现在长度恒为 2 的 `TRADE_SETTLE.postings` 中。

这使日志生产者和重放器无法唯一判断核销应属于最后一笔强平成交、`MARGIN_CALL`，还是另一个未定义事件。

**关闭条件**：二选一：

- 为 `MARGIN_CALL` 增加明确的代理账户及交易所风险账户分录；或
- 新增独立的 `DEFAULT_WRITE_OFF` 事件，冻结其优先级、因果外键和分录 Schema。

验收时必须证明仅凭事件日志即可从穿仓前状态重放至 `wallet=0`、`position=0`、`entry_notional=0`、账户状态 `LIQUIDATED`，并保持修正后的全局恒等式精确成立。

### 13.4 当前 P1 重要项

#### P1-F01【已关闭 · §14.2】：保证金率和杠杆档位的保守舍入未冻结

`initial_bp = 10000 / leverage_tier` 在 3x 档位被写为 3333 bp，会允许略高于 3 倍杠杆。建议规定：

```text
initial_bp = ceil(10000 / leverage_tier)
```

因此 3x 为 3334 bp。所需初始保证金、维持保证金、手续费预冻结和强平恢复线的整数乘除均须明确向交易所风险保守的舍入方向。账户合同示例中“向下取整对代理不利”的表述也应修正：所需保证金向下取整实际对代理有利。

#### P1-F02【已关闭 · §14.2 转 P1-G01→P1-H01，终结于 §17.2】：确定性 RNG 合同仍不可直接实现

规格同时要求 `SeedSequence` 和核心领域层仅使用 Python 标准库，二者在通常语义下冲突。策略合同指定 Box–Muller，但未冻结三角函数、π 常量及均匀随机数到开区间 `(0,1)` 的映射；Dirichlet 所需 Gamma 抽样、对数正态和其他分布变换也没有规范算法。

**建议**：定义纯标准库的语义键到随机比特映射，例如对规范编码后的语义键使用固定版本的 BLAKE2b，并冻结“比特串 → 开区间均匀数 → 各分布”的全部算法。标准正态可考虑不依赖三角函数的 Marsaglia polar 方法，但同样须冻结拒绝采样的 draw index 规则、Decimal 精度和 `ln`/`sqrt` 实现。

#### P1-F03【部分关闭 · §14.2 转 P1-G04→P2-H01，仍开放】：账户字段和旧制度术语尚未完全同步

当前仍可检出以下冲突：

- `event-schema.md` 仍使用 `reserved_cash_delta_units`，应统一为 `reserved_delta_units` 或明确的保证金字段；
- `agent-strategy.md` 仍称预冻结“名义金额与手续费上界”，与 ADR-005 已改为“初始保证金与手续费上界”冲突；
- ADR-005 §5 仍使用 `cost_cash_units`、`quantity_units` 等旧字段，没有同步 `entry_notional_units`；
- PRD、规格、方法论和指标字典仍散落“现金、库存、融资”等现货措辞；
- `required_quantity_units` 描述仍引用旧名 `target_ratio`；
- `MARGIN_CALL.caused_by_event_id` 仍保留已后移的收盘 `SNAPSHOT` 分支。

建议建立一次字段级术语表并用全文检索作为文档 CI，防止一个概念出现两套字段名。

#### P1-F04【已关闭 · §14.2】：强平重试与全账户扫描边界仍需明确

当前约定待强平账户只在下一笔成交改变 mark 后重试。如果新限价流动性已经进入订单簿但没有发生其他成交，之前取消的 IOC 不会立即重新提交。需要明确这是刻意的实验制度，还是应在相关流动性恢复时触发重试。

同时，成交改变风险 mark 后，受到影响的是所有持仓账户而不只是成交双方。实现合同应明确第一版采用 O(N) 扫描全部非零仓位账户，并规定同一次成交触发多个 `MARGIN_CALL` 时的确定性账户排序和 `chain_depth` 传播规则。

### 14.3 当前 P0 阻断项

#### P0-G01【已关闭 · §15.2】：风险账户在 C2 中的符号写反

账户合同 §2.3、指标字典 §5 和规格 SC-001 当前使用：

```text
Σ(wallet − entry_notional) + exchange_fee − exchange_risk = initial Σwallet
```

同时又定义风险账户为有符号量，交易所损失记负。穿仓核销时：

```text
Δwallet = +L
Δexchange_risk = −L
```

代入当前公式得到：

```text
ΔC2 = +L − (−L) = +2L
```

这与文档所称的“抵消”相反。正确联合恒等式应为：

```text
Σ(wallet − entry_notional)
    + exchange_fee
    + exchange_risk
    = initial Σwallet
```

此时核销变化为 `+L + (−L) = 0`。必须同步修正账户合同、指标字典、规格 SC-001、手工穿仓示例和对应测试名称。

**关闭条件**：用至少一条穿仓前后完整整数分录逐项代入，证明联合恒等式左右两侧完全相等；不得只依据“两个 delta 符号相反”口头判断。

#### P0-G02【已关闭 · §15.2】：仓位归零后的负钱包账户不会触发核销

账户合同 §5 要求核销开始时“仓位已全平、钱包为负”。但强平触发式要求 `position != 0`，事件 Schema 又规定成交改变风险 mark 后只扫描所有**非零仓位账户**。

因此最后一笔强平成交可能产生以下死角：

1. `position` 从非零变为 0；
2. 已实现损失使 `wallet < 0`；
3. 账户因仓位为 0 被排除在保证金扫描外；
4. 不生成 `verdict=BREACHED` 的 `MARGIN_CALL`；
5. 已定义的核销 postings 永远不会执行。

**关闭条件**：冻结成交后的两阶段风险检查，例如：

```text
1. 对本次 TRADE_SETTLE.postings 涉及的账户检查：
   position == 0 且 wallet < 0 → BREACHED
2. 对所有 position != 0 的账户执行保证金扫描
```

还须定义同一账户同时命中多个检查时的去重、事件顺序和状态转换，并增加“最后一手全平后钱包刚好为 −1 个最小单位”的验收案例。

#### P0-G03【已关闭 · §15.2】：PnL 桥接混用了 risk mark 与 valuation mark

指标字典 §3.1 规定用于未实现 PnL 的报告 `mark` 为 `mid`，缺失时退化为 `last`；代理合同 §3.3 则规定强平使用 `last`，并强调两者是不同口径。但指标字典 §5.2 又把 PnL 桥接中的 `mark` 定义成风险标记价 `last`。

翻仓示例进一步写成“成交价 98、同一成交后的 `mark_after=97`”。如果这里使用最近成交价，本笔成交后 `last` 必须等于 98，不可能为 97。

若严格令 `risk_mark_after = trade_price`，则每笔成交中：

```text
Spread + Impact
= q × (risk_mark_before − trade_price)
  + q × (trade_price − risk_mark_before)
= 0
```

这样虽然可以形成代数恒等式，却使价差和即时冲击永远互相抵消，失去研究指标意义。

**关闭条件**：明确区分并冻结：

- `risk_mark`：最近成交价，只用于保证金和强平；
- `valuation_mark`：建议为 `mid`，缺失时退化为 `last`，用于报告权益与 PnL 桥接；
- 成交事件须直接记录或可无歧义重建 `valuation_mark_before` 与 `valuation_mark_after`；
- 七种已验算情形必须按最终 valuation mark 口径重算，示例不得再出现成交后 risk mark 不等于成交价。

### 14.4 当前 P1 重要项

#### P1-G01【已关闭 · §15.2 转 P1-H01，终结于 §17.2】：随机算法规范仍有内部冲突

代理策略 §9 仍指定 Box–Muller，§10.3 又指定 Marsaglia polar，二者必须只保留一个。Gamma/Dirichlet 目前主要给出算法名称，尚未冻结 Marsaglia–Tsang 的完整接受条件、常量、每个 Dirichlet 分量的 draw-index 分配，以及 `u^(1/α)` 的 Decimal 实现规则。

BLAKE2b 语义键使用 `|` 拼接，但没有限制 `agent_id` 和 `mechanism` 是否允许包含分隔符。建议采用长度前缀编码或规范 JSON 数组，或者明确字段字符集，从格式上排除键碰撞。

#### P1-G02【已关闭 · §15.2 转 P0-H01/P1-H02，终结于 §17.2】：编码前验收包仍未完成

账户合同已列出十个语言无关验收案例，但明确说明案例 3、4、6—9 留待实现时补齐。它们包含部分平仓、翻仓、杠杆边界、强平重算、无对手方和穿仓重放，正是最容易改变状态机接口的场景。

这些案例应在账户引擎编码前给出完整输入、逐步状态和期望分录；否则“实现时补齐”实际上是让代码反向决定合同。

#### P1-G03【已关闭 · §15.2 转 P0-H02，终结于 §17.2】：订单保证金占用及自成交规则未闭合

当前只说明挂单按最坏情形占用 `reserved_units`，尚未给出同向多张挂单、反向挂单、部分成交和撤单后的精确增量/释放算法。实现前应给出“当前仓位 + 全部活动挂单分别可能成交”的最坏风险定义，避免逐单检查重复占用或低估占用。

文档也没有定义同一代理同时成为 maker 与 taker 时的行为。应明确禁止自成交、采用哪一种 self-trade prevention 规则，或允许自成交并冻结两条账户分录的应用顺序及费用结果。

#### P1-G04【部分关闭 · §15.2 转 P2-H01，仍开放】：旧术语与基准注释残留

仍需统一的典型位置包括：

- 代理策略 §9 的 Box–Muller 和 §11 的“融资利息”；
- BENCH-001 的 `initial_bp = 10000 / tier` 注释，应改为 `ceil(10000 / tier)`；
- PRD M1 的“现金守恒 C1 / 库存守恒 C2”；

核心字段已经基本统一，因此该项不单独阻断账户算法，但必须在首次正式实验前关闭，避免报告层重新引入旧口径。

### 15.3 当前 P0 阻断项

#### P0-H01【已关闭 · §17.2】：案例 7 的强平验收向量自相矛盾且数值错误

`acceptance-vectors.md` 案例 7 明确称“零费率以隔离重算逻辑”，但给出的首次强平量为 `288.678`。在该案例参数下：

```text
position = 500
equity = 2000
mark = 94
target = 10%
fee = 0

q ≥ 500 − 2000 / (94 × 10%)
  = 287.234042553...
```

按 `min_quantity=0.001` 向上取整，正确结果应为：

```text
q₁ = 287.235
```

文档中的 `288.678` 实际来自 **5 bps taker 费率**：

```text
2000 − q×94×0.0005 ≥ (500−q)×94×0.1
q ≥ 288.677429...
→ q = 288.678
```

因此案例的“零费率”与期望值不能同时成立。

更重要的是，文档让一半 `144.339` 成交后，在 mark 不变的情况下得到新数量 `143.614`。若使用 5 bps 并正确更新权益：

```text
equity_after = 2000 − 144.339×94×0.0005
             = 1993.216067

重新计算所需 q = 144.338429...
向上取整为 144.339
```

它恰好等于原剩余量，而不是 `143.614`。在线性公式、成交价和 mark 均不变时，仅仅部分成交并不会让剩余总需求神秘变化；要验证“必须重算且结果不同”，必须让部分强平成交改变 `risk_mark`，再使用新的价格、权益和手续费重算。

同一错误已摘要到 `margin-and-account.md` 的案例 7 说明中。该表自称实现的“唯一裁判”，因此错误期望值是直接编码阻断项。

**关闭条件**：重新设计案例 7，明确：触发时 risk mark、部分成交价、成交后 risk mark、手续费、成交数量、剩余仓位与权益；用最小单位整数给出二分搜索的最小可行值，并同时验证 `q−1 step` 不可行、`q` 可行。

#### P0-H02【已关闭 · §17.2】：`reserved_units` 公式重复占用当前持仓保证金且遗漏费用

代理策略 §11.1 当前定义：

```text
buy_all  = position + Σ(active buys)
sell_all = position − Σ(active sells)
required_reserved = IM(max(|buy_all|, |sell_all|))
reserved_units = required_reserved
```

当账户已有仓位、没有任何活动挂单时，`buy_all = sell_all = position`，因此
`reserved_units` 仍等于现有仓位的全部初始保证金。这与账户字段“挂单占用的保证金”矛盾。

随后账户合同 §3.3 又使用：

```text
available = equity − reserved_units
required margin of new total position <= available
```

新总仓位的 required margin 已包含当前仓位，再从 available 中扣一次当前仓位保证金，形成重复占用，合法订单会被错误拒绝。

此外，当前合并公式：

- 没有加入 ADR-005 要求的手续费上界；
- 用单一 `valuation_mark` 估算所有限价单，而不是冻结各订单可能成交价格的风险口径；
- 没有给出新增订单加入前后的 `reserved_delta_units`，无法直接生成事件分录。

**关闭条件**：二选一并统一准入公式：

1. `reserved_units` 只表示活动挂单相对当前持仓的**增量**初始保证金与费用上界；或
2. 将其重命名并定义为“持仓 + 挂单总风险占用”，同时改写 available 和准入式，不再重复扣除。

必须增加至少四个整数验收向量：已有持仓无挂单、同向多挂单、双向挂单、部分成交后撤单；每个向量同时断言 reserved before/after/delta 和准入结果。

### 15.4 当前 P1 重要项

#### P1-H01【已关闭 · §17.2】：拒绝采样的 draw-index 推进仍不可唯一实现

随机合同规定 Marsaglia polar 每轮可能因拒绝而消耗多个两元组，但又称 Marsaglia–Tsang “每轮消耗 2 个正态 draw + 1 个均匀 draw = 3”。两者不能同时成立：一次标准正态本身可能先拒绝若干对均匀数；并且当 `v <= 0` 时算法直接进入下一轮，根本不会消耗后面的均匀数。

合同还没有给出 Marsaglia polar 的完整伪代码、返回两个正态值时是否缓存第二个，以及子采样器如何把“下一个未使用 draw_index”返回给 Gamma 调用者。

**建议**：所有采样函数统一返回 `(value, next_draw_index)`，不得用“每轮固定消耗 3 个”描述嵌套拒绝采样。补入固定语义键下的前若干个均匀、正态、Gamma 和 Dirichlet 黄金向量。

#### P1-H02【已关闭 · §17.2】：验收表尚不是完整的整数事件裁判

案例 9 只写 A 的状态和风险账户，却用 `C2=505000`，这隐含对手方 B 的初始钱包约为 500000，但正文仅称其为“深口袋对手方”，没有给出 B 的完整初始状态、仓位、开仓成本和逐步钱包。

案例 9 的“mark→80（未成交）”也与“只有 `TRADE_SETTLE` 改变 risk mark”冲突。若指 A 未成交、由其他账户在 80 成交，应明确写出那笔成交及其账户分录；否则该状态在当前模型中不可达。

多数案例仍以人类十进制值而不是完整最小单位整数 postings 表示，案例 8 也只有事件名称而无完整字段。可读示例可以保留，但若要充当“唯一裁判”，应同时附机器可读或至少字段完备的整数向量。

#### P1-H03【已关闭 · §17.2】：账户合同中的裸 `mark` 仍有双重解释

指标字典和代理合同已经区分 `risk_mark` 与 `valuation_mark`，但账户合同的权益、名义价值、保证金、强平数量和资金费公式仍统一写作裸 `mark`。实现者仍可能把报告权益用于强平，或把 risk mark 用于 PnL。

建议定义 `equity(mark)` 基础函数，并显式命名：

- `risk_equity = equity(risk_mark)`，仅用于保证金、准入、强平和穿仓；
- `valuation_equity = equity(valuation_mark)`，仅用于报告和 PnL 桥接。

资金费使用哪一个 mark 也须明确，不能继续写裸 `mark`。

#### P1-H04【已关闭 · §17.2】：多笔撮合与风险扫描的原子边界未定义

一张主动订单可能连续吃掉多个价位，产生多条 `TRADE_SETTLE`。事件合同规定每条结算后生成同为 class 1 的 `MARGIN_CALL`，但没有说明 `ORDER_ARRIVAL` 是一次性预生成全部成交，还是“成交一笔 → 结算 → 风险扫描 → 继续撮合”。

若一次性预生成多个 class 1 结算事件，第一笔结算产生的 `MARGIN_CALL` 会因 `seq` 晚于已经入队的其他结算，无法保证在下一笔成交前执行；判定可能基于已变化的账户和 mark。应冻结批次原子性或引入明确的撮合 continuation 语义，并增加“一张大单跨三档、第二档后触发其他账户强平”的事件序列验收。

### 16.3 新增 P0 阻断项

#### P0-I01【已关闭 · §17.2】：架构计划的逐事件守恒断言遗漏 `entry_notional`

`plan.md` §5.2 当前要求：

```text
Σ postings.wallet_delta + fee_delta + risk_delta = 0
```

该断言在跨价换手时不成立。以第 13 节反例的第二笔成交为例：A 在 110 平掉成本 100 的多头，C 在 110 建新多头。该事件中：

```text
Σ wallet_delta = +10
Σ entry_notional_delta = +10
fee_delta = 0
risk_delta = 0
```

钱包变化并不单独归零；正确的逐事件价值断言应包含开仓成本：

```text
Σ(wallet_delta − entry_notional_delta)
  + exchange_fee_delta
  + exchange_risk_delta
= 0
```

**关闭条件**：修正 plan §5.2，并同步 M1 属性测试任务。使用案例 2 的第二笔跨价换手证明旧断言失败、修正后断言为 0。

#### P0-I02【已关闭 · §17.2】：ORDER、TRADE 和批次风险检查的事件生命周期不可实现

新撮合合同同时规定：

1. 撮合在 `ORDER_ARRIVAL(class 0)` 中同步完成；
2. 一张跨档订单生成多个独立 `TRADE_SETTLE(class 1)`；
3. 所有 `TRADE_SETTLE` “生成并结算完毕后”才执行批次风险检查；
4. 事件是从队列弹出后执行的一次原子状态转移。

在当前优先级下，同一时间戳的所有 class 0 事件都排在 class 1 之前。若 `TRADE_SETTLE`
按正常事件语义入队后才更新账户，则会出现：

```text
ORDER_ARRIVAL A（class 0）→ 生成 TRADE_SETTLE A（class 1，尚未处理）
ORDER_ARRIVAL B（class 0）→ 用尚未结算 A 的旧钱包/旧仓位做保证金准入
TRADE_SETTLE A（class 1）→ 此时才更新账户
```

这会允许同一时间戳内基于过期账户重复下单。若改为在 `ORDER_ARRIVAL` 内同步修改账户，随后 `TRADE_SETTLE` 就不再是引发账户变化的原子事件，而退化为事后记录，违反事件 Schema 和日志重放合同。

“整批后风险检查”同样缺少可执行载体：多个结算事件已经入队时，哪个事件知道自己是该批最后一笔？`MARGIN_CALL.caused_by_event_id` 应指向哪一笔？现有 Schema 没有 `batch_id`、`batch_index`、`batch_size` 或 batch-end/continuation 字段。

自成交阻止也有同类问题：撮合合同要求同步撤销 resting order，同时再写一条
`ORDER_ARRIVAL(action=CANCEL)`。若该取消事件之后仍会被处理，就会重复撤销；若不会被处理，它又不符合“事件是状态转移”的定义。

**关闭条件**：选择并完整定义一种事件模型，例如：

- 将撮合、逐笔结算和最终风险扫描定义为 `ORDER_ARRIVAL` 内的单一原子事务，而
  `TRADE_SETTLE`/取消记录明确降级为不可再次执行的 outcome records；或
- 引入逐笔撮合 continuation/batch 事件，使“取一笔 → 结算 → 继续撮合/批次结束”在事件队列中显式推进，并冻结同时间戳其他订单能否插队；或
- 重构 priority/class 与时间推进，使账户结算必定先于下一张依赖该账户状态的订单准入。

无论选择哪种，都须增加“两张同代理订单同时间戳到达，第一张成交耗尽保证金，第二张必须拒绝”和“一张大单跨三档后只做一次批次风险扫描”的完整事件序列。

### 16.4 新增文档的其他重要问题

#### P1-I01【已关闭 · §17.2】：撮合合同的逐笔 valuation mark 与整批原子性边界不清

撮合合同要求每笔成交记录逐步变化的 `valuation_mark_before/after`，但又把跨档撮合称为一个原子市场事件。如果订单簿在 `ORDER_ARRIVAL` 内一次性走完整批，必须明确每笔

### 19.3 新增 P0 阻断项

#### P0-K01【已关闭 · §20.1】：OB 向量使用不存在的记录类型，且“完整事件序列”遗漏必需记录

事件 Schema §1.4 只允许事务记录：`TRADE_SETTLE`、`MARGIN_CALL`、
`MARKET_DATA_PUBLISH` 和事务内 `CANCEL`。但订单簿向量在 OB-1/2/3/5/7 中新增了
`RESTED`，没有 Schema、priority class、字段表或哈希规则。OB-9 又在被拒绝的
`ORDER_ARRIVAL(record_index=0, accepted=false)` 后追加一个匿名
“`record_index=1（无成交，accepted=false）`”，同样没有事件类型。

与此同时，撮合合同 §1.2 规定每个成功订单事务末尾生成 `MARKET_DATA_PUBLISH`，但
OB-1—OB-7 普遍省略该记录；OB-5/7 还用 `RESTED` 占据了本应由行情发布使用的
`record_index`。因此这些表既不能按事件 Schema 序列化，也不是其自称的完整日志。

**关闭条件**：只能选一种统一方案：

1. 推荐：不新增 `RESTED`。挂簿结果由父 `ORDER_ARRIVAL`、成交/取消记录和事务后簿状态
   表达；每个改变盘口的成功事务补齐 `MARKET_DATA_PUBLISH`，拒单事务只有 record 0；或
2. 若确需 `RESTED`，先在事件 Schema/priority/E-002 中正式定义，提升
   `schema_version`，再统一 matching、向量、重放和任务。

无论选择哪种，OB-1—OB-9 的每个 `record_index` 都须重算，不能只改记录名称。

#### P0-K02【已关闭 · §20.1】：OB-8/OB-9 依赖保证金，但被列为无杠杆 0.1.1 的强制退出条件

0.1.1 明确规定保证金准入桩恒通过、强平和穿仓到 0.1.2 才实现；T306 也写明保证金检查
桩恒通过。但：

- OB-8 的前置是“某杠杆账户持有多头”，并期待 `MARGIN_CALL`；
- OB-9 要求第一张订单“耗尽保证金”，第二张因最新账户状态被拒；
- T204b/T308 与 E3 又要求 0.1.1 全部通过 OB-1—OB-9。

这在当前范围内不可达。OB-9 还没有给出钱包、仓位、entry、费率、两张订单价格/数量和
预期 reserved 整数，账户验收向量中也不存在与它一一对应的场景，无法构造其声称的
黄金日志。

**关闭条件**：拆分阶段裁判。0.1.1 只验证事务原子性、log key 顺序及“后续事务看到
已提交状态”（可用可注入的 admission spy/状态版本断言）；保证金拒单和实际
`MARGIN_CALL` 向量移至 0.1.2，并补齐字段完备的整数账户初态与 postings。同步修改
0.1.1 E3、T204b/T306b/T308 和 0.1.2 T104/T201 的引用。

#### P0-K03【已关闭 · §20.1，异常路径余项转 P0-L01】：`fill_count` 在首笔记录“立即写入”时尚不可知

事件 Schema §1.4 要求事务记录按实际发生顺序“立即写入日志”；撮合合同又要求第一笔
`TRADE_SETTLE` 就携带整次撮合的 `fill_count`。在跨档、自成交撤单和部分成交共存时，
只有完成整个撮合循环后才自然知道总成交笔数。当前任务没有规定预扫描、事务内缓冲或
日志回填，而规范序列化日志又不允许事后修改已写出的记录。

**关闭条件**：冻结一种实现合同并加入向量：

- 先在不可变簿快照上完整 dry-run，得到全部 fills/cancels 后再原子提交；或
- 事务内缓冲全部记录，撮合完成后填入 `fill_count`，再按 record index 一次性写出；或
- 删除 `fill_count`，改用可流式表达的 `is_last_fill`/事务结束记录。

选择前两者时必须说明 dry-run/缓冲与正式账户更新、STP 撤单、手续费及异常回滚的关系。

### 19.4 新增 P1 重要项

#### P1-K01【已关闭 · §20.1】：OB-8 把“一轮扫描”误写成“至多一条 MARGIN_CALL”

一次批末风险扫描只执行一轮，但事件 Schema §4.2.2 要对所有非零仓位账户 O(N) 扫描，
同一次成交可以按 `agent_id` 顺序产生多条 `MARGIN_CALL`。OB-8 固定
`record 4 MARGIN_CALL（若有）`、`record 5 MARKET_DATA_PUBLISH`，并称三笔成交“至多
产生一轮”，容易被实现成至多一条记录。

**建议**：写成 `MARGIN_CALL × m (m>=0)`，market data 的 record index 为 `4+m`；另给
一个 0.1.2 多账户触发向量验证排序和数量。

#### P1-K02【已关闭 · §20.1】：事务内 CANCEL 的事件类型与字段合同仍冲突

事件生命周期和新 OB-6/7 把它称为事务记录 `CANCEL`；撮合合同 §4 却要求“写入
`ORDER_ARRIVAL, action=CANCEL`”。事件 Schema 只有外部/队列 `ORDER_ARRIVAL` 的 CANCEL
字段表，没有事务内 `CANCEL` 的字段、priority class、`caused_by_event_id`、剩余数量或
reason 合同。实现者无法判断它是一个新的 event type，还是同类型但不入队的
`ORDER_ARRIVAL`。

**建议**：区分 `ORDER_CANCEL_ARRIVAL`（外部撤单指令/队列事件）与
`ORDER_CANCELLED`（IOC/STP 结果/事务记录），或明确复用方案并为两种生命周期分别冻结
必备字段。

#### P1-K03【已关闭 · §20.1，封闭性余项转 P0-L02】：新增 fill 字段没有进入摘要哈希合同

`fill_index/fill_count` 已成为 `TRADE_SETTLE` 必备字段和 OB 裁判，但 E-002 的纳入字段
清单没有它们，也没有逐笔 valuation mark、postings、margin verdict 等关键结果字段。
若分组、账本或 mark 错误而成交价量恰好相同，KPI-002 摘要仍可能相同。

**建议**：把所有影响重放和验收的语义字段按事件类型列成封闭清单；新增必备字段时由
Schema 校验强制同步 E-002。实现标识和因果 UUID 可继续排除。

#### P1-K04【已关闭 · §20.1，残留引用转 P1-L04】：版本化重构后追溯标识和发布版本语义没有统一

根规格编号已改为 `v0.1-belief-testing-laboratory`，但合同仍大量写“当前交付规格 001”、
任务仍引用 `[001 / D-1]`，README 的路径示例仍是 `specs/001-...`，并写不存在的
`milestones/` 子目录。README 还称 0.1.2/0.1.3 “任务待拆”，与实际文档冲突。

此外 `pyproject.toml` 是包版本 `0.1.0`，目录却把 0.1.1/0.1.2/0.1.3 同时称为里程碑，
尚未说明它们是否是可发布 SemVer、内部阶段号，或 v0.1 下的规格章节。若是 SemVer，
0.1.0 与 0.1.1 的先后和“完整 v0.1”含义相互打架；若不是，应避免使用看似补丁版本的

#### P1-K05【已关闭 · §20.1】：0.1.2 T507 的跨里程碑引用在重编号时失真

### 22.2 P0-L01 为什么不做回滚

第 21 章推荐「可提交工作副本」或「完整 undo log」，并把 fail-stop 列为需附加条件的
第三选项。本项目选择第三项，并按其要求停止使用「事务原子提交」这一表述——
事件 Schema §1.4 现明确区分**可见性原子性**（要求，单线程顺序执行天然成立）与
**失败原子性**（不要求）。

三条理由：

1. **不存在可恢复的异常类。** KR-006 违反、C1/C2 失衡、状态机非法转移，每一条都
   意味着代码是错的，不是市场出现了需要处理的情况。回滚的语义前提——「失败是预期
   内的，恢复后可继续」——在这里不成立；
2. **回滚买到的是最坏的结果。** 内核已经证明自己有缺陷，回滚让它继续跑并产出看似
   正常的日志与统计，而缺陷发生在哪个事务恰好被回滚抹掉了。研究工具的正确失败方式
   是大声地停下；
3. **成本落在每个事件上。** undo log 或写时复制是每事务都要付的分配开销，而 KPI-004
   的 10 秒门槛正是按事件吞吐量定的——为一个只在代码有 bug 时才触发的路径，向所有
   正常路径收税。

**代价必须说清**：异常发生时内存中的账户与簿处于不一致状态，且不可恢复。这被接受，
因为该进程随即终止，不一致状态不会被任何人观察到。已落盘的日志不受影响——`r0` 一并
缓冲保证了这一点。

### 22.3 关闭 P0-L02 时的连带发现

第 21 章指出「完成状态」在 §6 被写在日志**头部**。头部在运行开始时写出，那时结局
未知；更关键的是，进程被杀或磁盘写满时头部已经写好，日志看起来完全正常。因此完成
状态改为**尾部记录**，并新增 **TI-5**（缺少尾部记录）与 TI-4（内核自己写下 `ABORTED`）
配对——前者捕获「内核没来得及知道」的情形，后者捕获「内核知道」的情形。

只判其一都有洞：只看 `ABORTED` 会放过被截断的日志，只看「有无尾部」会把正常的
fail-stop 归入未知原因。

### 24.2 P0-M01 的关键判据：`null` 不等于 `0`

### 24.3 P2 行尾空格不修的理由

### 26.2 P0 阶段阻断项

#### P0-O01【已关闭 · §27.1】：字段注册表元合同仍未闭合（承接 P0-N01）

第 25 章的四项冲突仍全部成立，并补充发现两处作用域误述：事件 Schema §1.7 与 E-002
都把 `schema_version`、`event_id` 等称为“所有日志记录/全部记录共有”，但日志现已包含
`RUN_HEADER`、`EVENT`、`RUN_TRAILER` 三类顶层记录；这些字段实际只由 EVENT 共有。

当前冲突合计为：

1. `WRITE_OFF_POSTING` 表实际有 8 个叶字段，Schema §4.2.3/E-002 与 T204g 写 7 个；
2. T204f 要求六类字段元数据，Schema 的“同步强制”仍只要求四类；
3. 必备的 `EVENT.record_kind` 没有进入哈希纳入或排除集合；
4. `RUN_HEADER` 没有与 `RUN_TRAILER` 对称的字段名、类型、可空性、格式/枚举和哈希表；
5. “所有记录共有字段”的文字没有限定为 EVENT，会让三种顶层记录错误继承同一结构。

**关闭条件**：完整执行 §25.3 的五项关闭条件；同时把 §1.7/E-002 的“全部记录”改为
“全部 EVENT 记录”。由一个机器可读注册表生成三种顶层记录、两种 posting 变体和 E-002
投影测试，不再维护相互独立的手抄字段数。

#### P0-O02【已关闭 · §27.1】：内核工作量、日志 EVENT 与文件记录三种计数混用，精确终止可能切断事务

指标字典把 Event 定义为“日志中的一条全序记录”并称其为内核工作负载单位；引入 header/
trailer 后，并非每条日志记录都是 EVENT。BENCH-001 又要求恰好处理 `max_events=100000`
个 events，但队列弹出的事件会执行一个原子事务，一个事务可生成数量不定的 EVENT 记录。

若 `max_events` 按 EVENT 日志行计数，达到阈值时可能位于事务中间，与“事务一次性提交所有
记录”冲突；若按出队事务计数，则吞吐量 `max_events / time` 与指标字典的 Event 定义冲突。
header/trailer 加入后，文件总记录数又是第三个数。

**关闭条件**：在指标字典、事件 Schema、BENCH-001/002、benchmark README 和 T702 中
冻结三个不同名称，例如：

- `processed_transactions`：成功提交的队列事务数；
- `event_record_count`：`record_kind=EVENT` 的记录数；
- `file_record_count`：含 header/trailer 的文件记录数。

性能预算只能选择一个明确单位。终止检查必须发生在事务边界，并明确达到阈值后是允许
最后一个事务造成有限超出，还是在执行事务前按可知成本停机；不得在事务提交中间截断。

#### P0-O03【已关闭 · §27.1】：FR-019/FR-020/SC-008 是 v0.1 必选项，但没有里程碑负责交付

v0.1 总规格与 PRD 要求单文件 HTML 回放、K 线视图以及“只凭日志完整回放”。0.1.1 把
FR-019/020 标为 0.1.2；0.1.2 又明确排除并后移到 0.1.3 或按需；0.1.3 tasks 再次明确
推迟到后续展示阶段，退出条件也没有 SC-008。结果是 0.1.1—0.1.3 可以全部签收，而完整
v0.1 仍未交付产品规格中的必需功能。

**关闭条件（二选一）**：

1. 在 0.1.3 增加 HTML 回放/K 线的任务、输入输出合同、无服务端单文件约束和 SC-008
   退出测试；或
2. 正式把 FR-019、FR-020、SC-008、PR-018—PR-020、KPI-012 移到 v0.2，并同步 PRD、
   v0.1 总规格、计划和各里程碑的范围声明。

不能继续用“0.1.3 或按需”表示必选需求的归属。

#### P0-O04【已关闭 · §27.1】：M2 保证金扫描对安全账户是否产生日志、`LIQUIDATING` 如何使用均未定义

事件 Schema 的 `MARGIN_CALL.verdict` 含 `OK | PENDING_LIQUIDATION | LIQUIDATING |
BREACHED`，并用“本次检查安全”解释 `OK`；这可被理解为扫描到的每个非零仓位账户都要
生成 MARGIN_CALL。账户合同只定义跌破维持保证金时的 BREACHED/PENDING 行为，OB-8 又
主要描述跌破账户，所以实现也可合理地只记录不安全账户。

`LIQUIDATING` 没有出现在账户状态机 `ACTIVE ↔ PENDING_LIQUIDATION → LIQUIDATED` 中，
也没有生成时点。不同解释会改变每笔交易后的日志条数、摘要哈希、性能与链深统计。

**关闭条件**：在账户合同与事件 Schema 中冻结：

- 扫描集合与稳定排序；
- 哪些账户必然生成 MARGIN_CALL；
- `OK` 是每次安全扫描都记录，还是仅用于 pending 恢复；
- `LIQUIDATING` 的状态/事件时点与转移，或删除该枚举；
- 一次多账户扫描的完整记录顺序和 `m` 的含义。

补一份包含安全、首次跌破、已 pending、恢复与进入强平五种账户的完整 OB-8 黄金向量。

#### P0-O05【已关闭 · §27.1】：`grace_ns > 0` 的强平时间、恢复和因果链不可实现

总规格和配置保留 `grace_ns`，并声明宽限期结束后再强平；调度合同只给出
`MARGIN_CALL → ORDER_ARRIVAL` 的 `liquidation_latency_ns`，同时强调 grace 与 latency
不是同一个参数，却没有定义两者如何组合，也没有宽限期到期事件。当前只能实现默认
`grace_ns=0`，无法实现合同允许的非零配置。

**关闭条件**：选择并冻结一种模型：

- 简单模型：`forced_order_ts = breach_ts + grace_ns + liquidation_latency_ns`；或
- 显式模型：新增 grace-expiry 队列事件并定义其同时间戳优先级。

两种模型都必须说明宽限期内价格/权益恢复时是否取消强平、何时重新检查、父事件与
`risk_mark_event_id` 指向谁，以及重复跌破是否重置计时。为 `grace_ns=0` 和 `>0` 各补
一条黄金时序。

### 26.3 P1 重要缺口

#### P1-O01【已关闭 · §27.2】：0.1.1 的“确定性回放全部跑通”没有独立验证完整订单簿状态

0.1.1 目标同时包含订单簿、账户、事件日志与确定性回放。T603 的独立验证器重建账户
终态并检查因果/C1/C2；T308 检查实时执行后的最终订单簿，但没有从日志独立重建订单簿
再对比终态。事件 Schema 声称可以由订单到达、成交和取消重建静态簿，这一能力目前没有
task 或退出条件证明。

**关闭条件**：扩展独立验证器，使其只读取日志，重建账户和订单簿两类终态，并与内核
快照逐字段比较；覆盖部分成交、IOC、STP 与 agent cancel。若项目只承诺账户回放，则必须
收窄 0.1.1 的目标措辞，但不推荐收窄。

#### P1-O02【已关闭 · §27.2】：TI-4/TI-5 复合异常优先级仍未冻结（承接 P1-N01）

一份结构损坏且 trailer 写 `ABORTED` 的日志仍可能同时命中 TI-4 与 TI-5。

**关闭条件**：先验证 JSON、trailer 存在性和 `record_count`；任一结构错误判 TI-5。仅在
结构完整后解释 `terminated`，完整的 ABORTED 才判 TI-4。为 `ABORTED + record_count
mismatch` 增加组合测试。

#### P1-O03【已关闭 · §27.2】：OB-8/OB-9b 的黄金预言与实现任务混在一起

OB-8 仍是步骤骨架，没有完整账户整数、分录和事件结果；OB-9b 明示完整值待 0.1.2 补。
T104/T201 同时负责补向量和写实现，会让实现者在看到代码结果后反向选择“黄金”答案，
削弱设计阶段向量作为独立预言的价值。

**关闭条件**：在 M2 编码任务前拆出合同冻结门，由独立的 Phase 0 task 先写完整 OB-8/
OB-9b 初态、逐步整数计算、postings、事件顺序和终态；评审通过后 T104/T201 只消费向量。

#### P1-O04【已关闭 · §27.2】：基准配置的 `schema_version` 与事件 Schema 版本同名异义

BENCH-001/002 顶层写 `schema_version: 1`，事件记录当前又要求 `schema_version=2`。如果
前者是 benchmark 配置格式版本，应明确命名；如果要注入 RUN_HEADER，则数值错误。

**关闭条件**：配置字段改为 `config_schema_version`；另显式设置或引用
`event_schema_version: 2`，并说明二者分别由谁消费。

#### P1-O05【已关闭 · §27.2】：分析指标缺少零/负分母与无双边报价的空值规则

指标字典尚未定义：`equity <= 0` 时杠杆率如何表示、峰值权益 `<= 0` 时最大回撤如何计算、
无 `mid_before` 时价格冲击是否排除，以及钱包指标是直接读取 `wallet_units` 还是用“可用
钱包 + 占用保证金”重建。这些边界会让 T501/T502 的不同实现产生不同汇总值。

**关闭条件**：逐指标增加有效域、null/排除规则、分母为零/负数的处理和汇总时 null 的
传播方式；钱包指标统一为账户合同中的字段口径，避免把 reserved margin 重复相加。

#### P1-O06【已关闭 · §27.2】：代理下单的手续费预留没有明确覆盖预撮合成交量

代理合同把手续费上界写成“活动及候选单的剩余量”之和。候选单预撮合后既有立即成交量
又有入簿剩余量；若“剩余量”只指入簿部分，会漏掉本次立即成交的 taker fee。

**关闭条件**：把上界公式拆为“预撮合的逐 maker-price 成交手续费 + 入簿剩余量按预留
价格计算的手续费”，并加一条跨价位、部分入簿的 crossing order 向量。

#### P1-O07【已关闭 · §27.2】：需求到 task/退出条件没有机器可核验的完整追踪矩阵

当前没有重复 task ID 或悬空 task 引用，但多项总规格需求没有显式 owning task/exit 标签；
HTML 回放的归属遗漏正是其后果。依靠自然语言和人工链接无法保证后续移动范围时同步更新。

**关闭条件**：增加单一的 requirement → milestone → task → exit 矩阵；每个 FR/KR/NFR/SC
必须是“已拥有”“明确后移”或“删除”之一，CI 拒绝没有归属的必选需求。矩阵应由规格真源
生成或校验，不再在 PRD 和 tasks 中分别手抄。

#### P1-O08【已关闭 · §27.2】：PRD 仍在唯一真源声明后手抄 OB 集合（承接 P1-N02）

当前集合虽正确，但维护规则自相矛盾。

**关闭条件**：PRD 仅链接 spec E3，或从机器源生成集合；不要人工复制 ID。

### 26.4 P2 表达与维护项

### 28.3 P0 阶段阻断项

#### P0-P01【已关闭 · §29.1】：注册表仍不能从文档生成唯一的 EVENT/SNAPSHOT 模型

P0-O01 尚未真正关闭，存在两层直接证据：

1. `0.1.1 tasks` T204g 同一任务先写 `WRITE_OFF_POSTING` 为 **7** 个叶字段，五行后又
   断言为 **8** 个；实现仍无法同时满足两句；
2. 事件 Schema 的“同步强制”要求每个字段有记录类型、值类型、枚举值域、可空性、
   必备性和哈希分类六项，但 §4 的 EVENT 表大多仍只有“字段/说明”两列。尤其
   `SNAPSHOT.payload` 只写“账户或订单簿完整状态”，没有账户字段、订单簿层级结构、
   类型、排序或可空规则；注册表仍必须自行发明其 Schema。

这不是要求把注册表代码提前写进文档，而是当前规范输入本身不足以让两个实现者得到同一
模型。T204f2 只能证明实现内部三者同源，不能证明它与合同含义相同。

**关闭条件**：

- T204g 的 7 改为 8；
- 为每种 EVENT 增加完整字段元数据表，或新增一份机器可读 Schema 作为规范真源；
- 把 `SNAPSHOT.payload` 建模为 ACCOUNT/BOOK 判别联合，冻结叶字段、排序与空值；
- 增加 contract fixture，证明文档/机器 Schema 与 registry 生成结果一致，而不只是
  registry、serializer、hash 三个实现模块彼此一致。

#### P0-P02【已关闭 · §29.1】：只读日志缺少强制初态，T603 与 0.1.4 不能重建“各账户逐帧完整状态”

0.1.4 T103 要求仅按日志逐事务产出价格、盘口和**各账户**完整状态，T401 再与原运行
逐帧逐字段比较。但当前 RUN_HEADER 只有配置哈希、种子和单位，没有：

- 代理/账户全集与稳定顺序；
- 每个账户的初始钱包、仓位、entry、reserved、状态；
- `initial_price` 与初始订单簿；
- 强制的 `t=0` ACCOUNT/BOOK snapshot。

周期性 SNAPSHOT 的频率可配置，且 payload 尚未结构化。成交 posting 的 after/delta 只能
恢复**发生过分录的账户**，从未交易的账户不会凭空出现在日志中。因此不借助配置文件或
内核对象，T603 无法可靠重建完整账户终态，0.1.4 更无法生成第一帧和逐帧全账户状态。

**关闭条件（二选一）**：

1. RUN_HEADER 内联版本化的 `initial_state`（账户全集、初始市场状态、稳定排序）；或
2. 强制日志在任何业务事务前写出结构化的 t=0 ACCOUNT 与 BOOK snapshot。

两种方案都要冻结 payload Schema、初始帧是否计入 `processed_transactions`、帧边界
（推荐每个已提交事务后）以及 T401 的独立 oracle 采集方式。T603/0.1.1 E6 与 0.1.4
T101—T103/T401 同步使用同一初态合同。

#### P0-P03【已关闭 · §29.1】：“只记录状态转移”与部分强平后的 required quantity 重算直接冲突

事件 Schema §4.2.2 与 0.1.2 T202 规定：只有账户状态变化才写 MARGIN_CALL；
`PENDING_LIQUIDATION` 且仍不足时不写记录。账户合同 §4.3 又规定：强平部分成交后按
新状态重算 `required_quantity_units`，**每次重算都产生新的 MARGIN_CALL**。

部分成交后账户通常仍是 `PENDING_LIQUIDATION → PENDING_LIQUIDATION`，没有状态转移，
却发生了必须记录的新风险决定。两个实现分别遵守任一合同都会违反另一份。

**关闭条件**：把“记录集合”从纯状态转移改为明确的**可行动风险决定**集合，至少区分
首次进入 pending、恢复、穿仓和部分成交后的数量重算；或为重算增加独立事件类型。
同时定义 OB-8 的 `m` 是否只统计批末扫描转移，不包含强平重算，并给部分成交重算一条
完整事件向量。

#### P0-P04【已关闭 · §29.1】：`PENDING → ACTIVE` 恢复后，已排队的强平单没有取消或重校验规则

首次跌破时系统立即调度 `timestamp + liquidation_latency_ns` 的强平 ORDER_ARRIVAL。
在该延迟窗口内，其他成交可能让账户恢复并记录 `OK`，状态回到 ACTIVE；但已经入队的
强平单不会自动消失。当前合同没有说明到达时应取消、拒绝、重算还是照常卖出，后者会
错误强平一个健康账户。

**关闭条件**：为强平意图增加稳定 generation/token，并在 ORDER_ARRIVAL 到达时重验
账户仍为 pending 且 token 最新；恢复时使旧 token 失效。冻结失效订单是写
`accepted=false + reject_reason=LIQUIDATION_STALE`，还是产生专用取消记录，并定义
reserved、因果链和摘要字段。OB-8/T007 增加“延迟窗口内恢复”向量。

### 29.3 P0-P01 的解法为什么换了方向

前几轮一直在往 Markdown 里加表格，这轮不再加。

**Markdown 表达不了这件事**：六项元数据 × 约 60 个字段 × 嵌套变体，写成表格上百行
且无人能核对——本文档已经在一个 8 字段的结构上数错过一次，而且是在**刚刚加完计数
断言的同一轮**里数错的。

因此规范真源改为 `event-schema.fields.json`，与合同同级、随合同评审；Markdown 只
负责解释**为什么**。用 JSON 而非 YAML 是因为注册表要被 L1 核心层加载，KR-005 禁止
第三方依赖，`json` 在标准库。

T204f3 的双向检查是关键：只查「文档字段都在 JSON 里」会漏掉 JSON 单方面新增的字段，
只查反向会漏掉文档单方面新增的。**两个方向都查，才是一致性。**

### 29.4 P0-P02 与 P0-P04 是同一类缺陷

两者都是「合同描述了稳态，但没描述边界时刻」：

- P0-P02：描述了每个事务后的状态如何记录，**没描述第一个事务之前的状态从哪来**；
- P0-P04：描述了跌破后调度强平单，**没描述调度与到达之间的窗口里发生什么**。

这类缺陷在设计阶段最难自查——因为写的人脑子里默认「初始状态当然是配置里那样」
「强平单当然会执行」。它们只在**只读日志**和**延迟窗口**这两个真实约束下才暴露。

### 29.5 结论

**0.1.1 恢复全面 Go。** 事件模型的规范输入首次成为机器可读的单一真源，只读日志
首次具备重建第一帧的能力。

**本轮首次给两条「单一真源」配了机器强制**：T204f3（合同↔Schema）与 T607（需求
矩阵）。此前这两处都只是文字约定——而 §27.5 已经预警过它们是漂移面。

**仍然为真的限制**：全部向量期望值为人工推算；`event-schema.fields.json` 本身尚未
编写（T204f0），在它写出并通过 T204f3 之前，本合同的字段部分仍是待验证状态。

### 30.3 P0 阶段阻断项

#### P0-Q01【已关闭 · §31.1】：被声明为“唯一规范真源”的 JSON 不存在，P0-P01 只是后移成任务

事件 Schema §E-002 现在规定 `docs/contracts/event-schema.fields.json` 是字段名、类型、
枚举、可空性、必备性和哈希分类的唯一规范，registry 在运行时直接加载它；但仓库里没有
这个文件。T204f0 被安排在实现任务中“编写规范真源”，等于让实现者在写 registry 的同一
阶段重新决定那约 60 个字段的合同，这正是 P0-P01 要消除的问题。

第 29 章自己也承认“文件尚未编写、字段部分仍是待验证状态”，因此不能同时宣告事件模型
全面 Go。

**关闭条件**：

1. 在任何事件模型代码前实际提交完整 JSON；
2. 给 JSON 自身提供 meta-schema/加载校验和至少一组合法、非法记录夹具；
3. 把 T204f0 从实现任务改为**已完成的设计冻结门**，T204f 只消费；
4. 解决发布位置：当前 wheel 只打包 `src/market_game_sim`，运行时读取 `docs/contracts`
   在安装后的 wheel 中不可用。规范文件应放入可由 `importlib.resources` 读取的包数据，
   或增加明确的构建复制步骤与安装后测试，不能依赖仓库工作目录。

#### P0-Q02【已关闭 · §31.1】：t=0 SNAPSHOT 是第三种 EVENT 语义，但现有模型只允许队列事件/事务记录

事件 Schema §1.4 把 EVENT 分为两类：队列事件从队列弹出，事务记录由父队列事务产生；
`SNAPSHOT` 被明确列为 class 5 队列事件，队列事件必有 `enqueue_seq`。新 §4.6.3 又规定
t=0 的两条 SNAPSHOT：

- 不是队列事务，不计入 `processed_transactions`；
- 两条共享 `transaction_seq=0`，record index 为 0/1；
- 没有说明 `enqueue_seq` 是必备、null 还是不存在，也没有父队列事件。

它们因此既不符合“SNAPSHOT 是队列事件”，也不符合“事务记录由父队列事件产生”。同时
§6 仍允许 `EVENT*` 为零条，RUN_TRAILER 在“无已提交事务”时规定
`last_committed_transaction_seq=null`；完成运行现在却原则上至少有两条初始化 EVENT，
其最大 transaction seq 为 0。验证器可以合理地产生多种实现。

**关闭条件（二选一）**：

1. 把初态放入 RUN_HEADER 的结构化 `initial_state`；或
2. 正式定义“初始化事务”这一第三类来源，明确其 priority class、`enqueue_seq`、
   `processed_transactions`、哈希、失败语义、合法日志最小形状，以及零业务事务时 trailer
   的 `last_committed_transaction_seq`。

同步 §1.4/§3/§5.2/§6/E-002、T204e3/T204f0/T603，并增加“零业务事务正常完成”和
“初始化第二条写出失败”两条逐字节日志向量。

#### P0-Q03【已关闭 · §31.1】：数量重决策会生成新强平动作，却不会使旧的排队订单失效

当前 generation 只在 `ACTIVE → PENDING` 和 `PENDING → ACTIVE` 时递增。新规则又要求
`PENDING → PENDING` 且 `required_quantity_units` 改变时记录一个“新的下单数量”。

若这个新决定调度新强平单，旧单仍携带相同 generation，两个到达时都会通过验证，账户
可能被重复/过量强平；若不调度新单，“可行动的新下单数量”就没有任何动作。合同没有说明
哪一种，P0-P03/P04 只解决了恢复场景，没有解决 supersession。

此外 `liquidation_generation` 尚未进入账户合同 §1 的账户字段，也没有初始值；
MARGIN_CALL 本身不记录 decision 后的 generation。若运行在新单到达或周期快照前终止，
日志摘要无法直接观察实际代次是否更新正确。

**关闭条件**：每次产生替代性强平决定时 generation 都递增并只保留最新代，或明确不
并发调度而是在唯一在途订单到达时重算。冻结初始值、账户字段、MARGIN_CALL 的
`liquidation_generation_after`（或等价可重放字段）、旧订单拒绝行为和 reserved 变化；
T007 增加“pending 期间连续两次 q 变化、三张订单按乱序到达”的向量。

#### P0-Q04【已关闭 · §31.1】：`chain_depth` 的来源不存在，且“继承”与“+1”同时生效

事件 Schema §4.2.2 写“由成交直接触发的判定为该成交的 `chain_depth`”，但
TRADE_SETTLE 没有 `chain_depth` 字段。0.1.2 T204 又要求强平 ORDER 保留
`trigger_event_id`、`chain_depth`，而 ORDER_ARRIVAL Schema 两个字段都没有；实际因果
字段是 `decision_event_id → MARGIN_CALL`。

更关键的是，事件 Schema 规定强平成交后的判定为父判定深度 `+1`，账户合同 §4.3 对
部分成交后的同账户重算却规定“继承父判定深度”。同一批扫描还可能同时包含：

- 原强平账户的续单重算；
- 新被价格冲击拖入 pending 的账户；
- 早已 pending、现在 q 再变化的第三个账户。

三者不应无条件得到同一个深度。当前实现无法唯一决定连锁深度和规模，旗舰指标会受影响。

**关闭条件**：以 `ORDER_ARRIVAL.decision_event_id → 触发 MARGIN_CALL` 为唯一来源，按账户
角色冻结规则：同一账户续单保留原 depth；本次强平成交新触发的账户为 parent+1；已有
pending 账户的重决策保留其自身链归属，除非明确合并链。删除不存在的
`trigger_event_id`/TRADE_SETTLE.chain_depth 表述，并在账户状态或 MARGIN_CALL 中记录
重放所需的当前 chain id/depth。T007 增加三账户同批向量。

### 31.2 P0-Q02：初态快照不需要新概念

审计给了两个方案（塞进 `RUN_HEADER`、或定义第三类「初始化事务」），两个都不取。

**初态快照本来就可以是两个真正的队列事件**：`SNAPSHOT` 已经是 class 5 队列事件，
在 `timestamp = 0` 预先入队 `ACCOUNT`（`enqueue_seq=0`）与 `BOOK`（`=1`），
弹出后形成 `transaction_seq = 1` 与 `2`，业务事务从 `3` 开始。

这样字段、`enqueue_seq`、哈希、失败语义**全部沿用现有二分法，零新增概念**——
而另两个方案一个要在头部复制整套 payload schema（第二份定义），一个要为新类别单独
规定 priority class、计数、哈希与合法日志形状。

**它们计入 `processed_transactions`**：写出 190 个账户的全量快照是真实工作量，
计入比不计入更诚实。由此还收紧了两处形状约束——正常结束的日志**至少 2 条 EVENT**，
`last_committed_transaction_seq` 正常结束时**恒 ≥ 2**，「零业务事务的正常运行」
是合法的且值为 2。

### 31.3 P0-Q04 的三条规则为什么必须分开

此前事件 Schema 写「+1」、账户合同 §4.3 写「继承」，看似矛盾，其实**说的是不同账户**：

- **同一账户的续单重算** → 继承，不 +1。同一条链上的同一个受害者，链条没有延长；
- **本次强平成交新拖入的账户** → 父判定 +1。链条确实延长了一节；
- **已在别的链中 pending、本次仅数量重算** → 保留其自身链归属。

只用一条规则时，同一批扫描里这三种账户会被赋予同一个深度，连锁规模与深度这两个
旗舰指标随之失真。新增 `chain_id` 是为了把「深度」与「属于哪条链」分开——只有深度
无法区分它们，而「每条链的规模」需要分组才能报告。

### 31.5 结论

**0.1.1 全面 Go，且这次有实际产物支撑**：事件模型的规范输入不再是「将来会写的
JSON」，而是仓库里可加载、可校验、已通过计数与元数据完备性检查的文件。

P0-Q01 是同一类问题（人读的表 vs 机器读的源），应在 T607 实现时一次解决，现在
预先设计一套 grammar 只会多一份需要同步的东西。**已记为 T607 的已知限制。**

消费过，它的正确性要到 T204f/T204f3 才被检验。
