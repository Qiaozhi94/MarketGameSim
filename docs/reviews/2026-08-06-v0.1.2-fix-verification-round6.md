## 1. §1.10 `agent_initial_bp`——确认已修复

- **代码位置**：`experiment/runner.py:126-128`
  ```python

      s.agent_id: _compute_initial_bp(s.leverage_tier) for s in config.agent_specs
  ```

  策略侧（`strategy.py::order_intent_from_signal`）和撮合侧（`matching.py::_reserved_for`

  两条路径构造上保持一致。

- **决定性验证**（相同钱包 1000 人民币单位、相同订单 5000 notional）：
  ```

  ```
  这在修复前不可能——之前所有账户都被 `_INITIAL_MARGIN_BP_011=10000` 强制限制为 1 倍
  杠杆，与 `leverage_tier` 无关。

- **闭环验证**：tier=8 账户开出 5 倍杠杆仓位后价格从 100 跌到 75：

  与手算完全吻合。

- **局限**：未能通过完整 `run_one()` 自主决策流程复现（该函数把账户钱包硬编码为

  测试便利性的限制，不是接线本身的缺陷，因为策略定价与撮合准入两个环节都已直接验证。
  **仓库测试套件本身没有任何回归测试覆盖这个接线**（复核中的验证脚本是复核者自行构造的）。

**判定：已修复。** 连续三轮被列为最高优先级后，本轮确认解决。

## 2. §1.9 `LIQUIDATION_STALE`——核心问题已修复，有残留边界缺口

- **代码位置**：`book/matching.py:72-86`

- **独立复现1**（第三组参数：`wallet=7500, position=700, entry=70000`，与前几轮均不同）：
  账户 A 在 mark=93 触发 `PENDING_LIQUIDATION`（gen=1），延迟窗口到期前价格恢复到 99
  （`verdict=OK`，gen=2）。延迟到期后过期订单到达：
  ```
  ORDER_ARRIVAL origin=LIQUIDATION gen=1 accepted=False reject=LIQUIDATION_STALE
  Final A position_units: 700000（未被过量强平砍仓）
  ```

- **独立复现2**（账户合同 T202b 验收用例②：三张单乱序到达）：构造三个真实世代（gen=1/2/3，
  `required_quantity` 各不相同），以 `[gen=2, gen=3, gen=1]` 乱序喂给 `match_order()`：
  ```
  g2(mid):     accepted=False reject=LIQUIDATION_STALE
  g3(newest):  accepted=True  reject=None
  g1(oldest):  accepted=False reject=LIQUIDATION_STALE
  ```
  只有当前世代通过，与到达顺序无关——检查是"基于当前状态"而非"基于到达顺序"，架构稳健。

- **确认存在的残留缺口**：若强平单未携带 `liquidation_generation`（`matching.py:506`
  `event.setdefault("liquidation_generation", None)` 会把它填成 `None`），第二个校验分支
  `if order_gen is not None and ...` 整体被跳过，账户处于 `PENDING_LIQUIDATION` 状态时该
  订单会被**无条件放行**。经代码核对，当前生产路径（`_run_post_batch_risk_check` →
  `kernel.enqueue`）总是显式传入整数世代号，**这个缺口目前不会被生产流程触发**，不是活跃
  bug，但 `match_order` 对"强平单必须携带世代号"这件事没有强制约束，是真实的设计脆弱点。

- **测试覆盖为零**：全仓库没有任何测试文件提及 `LIQUIDATION_STALE` 或
  `liquidation_generation` 的强平场景，本轮的验证全部是复核者自行构造的脚本。

**判定：部分修复**——核心资金损失问题解决，架构经乱序到达验收用例验证是稳健的，但存在
一个已知（当前不可达）的边界缺口，且完全没有回归测试保护。

## 4. 本轮确认的其他真实修复

### 4.1 §1.6 报告数据语义错位——已修复

`runner.py` 新增 `from market_game_sim.metrics.sampling import sample_agent_series`，
`build_study_report` 不再拼接错位元组，改为对每个样本调用 `sample_agent_series` 取真实

`sample_market_series` 仍未被使用）。

### 4.2 §1.5 herding 因子——真实修复（momentum 因新 bug 仍未修复）

`world["trade_history"]` 五轮以来首次有了写入点（`matching.py::_record_trade_history`），
但写入的 `timestamp` 被**硬编码为字面量 `0`**。真实 3 代理场景实测：无论发生多少笔成交，
`_bars_from_history` 永远只能产出 1 根 K 线。

这导致 momentum 和 herding 命运分叉：
- `momentum(bars, lookback=5)` 要求 `len(bars)>=6`——恒不满足，**momentum 仍恒为 0**，
  但原因从"上游数据管道缺失"变成了"上游管道写了但写错了"（新 bug）。
- `herding(window)` 只要求非空——1 根 bar 就够，**实测 herding=-1（真实非零值）**，
  确认真接入。

Dirichlet 权重合成仍未接入（`weights=[0.2]*5` 字面量未变，`dirichlet_draw` 生产路径零
调用）。

### 4.3 §2.14 边界 bug——已修复（函数仍是死代码）

`if tr.timestamp else` 误判 `timestamp=0` 的边界缺陷已修正为 `is not None`。但
`aggregate_bars` 本身仍零调用点，生产路径走的是 `handler.py` 里的独立实现
`_bars_from_history`，同样受 §4.2 提到的时间戳硬编码拖累。

## 8. 建议

1. **§1.9 的残留缺口（世代号为 None 时绕过检查）建议加一行防御性代码**：在
   `_run_post_batch_risk_check`/订单构造处强制断言强平单必须携带非 None 的
   `liquidation_generation`，或在 `match_order` 里把 `order_gen is None` 也视为
   `LIQUIDATION_STALE` 拒绝，消除这个当前"理论存在但不可达"的脆弱点。
2. **§1.8 的绕过反例2需要修复**：`decision_ids` 为空集合时不应跳过检查，应改为"存在
   `origin=AGENT` 订单但日志中零 `AGENT_DECIDE` 事件"本身就判定为 KPI-006 失败。
3. **本轮三项最关键的修复（§1.9/§1.10/§1.8）都没有配套回归测试**，建议优先把复核脚本
   （见各节描述的复现场景）转化为正式测试用例并入库，这是防止这些来之不易的修复被
   后续改动无意间回退的唯一可靠手段。
4. **`metrics/bridge.py` 需要接入 `runner.py`/`verify.py`**，否则 T503 会重演
   `metrics/sampling.py` 曾经历的"孤儿模块"阶段。
5. §2.16 建议实现真正的动态续约（在 `kernel.run()` 内部循环中消费
   `pending_reschedules`），而不是继续加大静态预排上限。
6. 在 §1.8 剩余绕过路径、§1.9 残留缺口、§2.7 Phase 6 统计口径解决之前，仍不建议宣布
    E1–E7 全部达成，但可以考虑单独确认 E2/E5 是否能通过补充端到端测试来达成——这两项
    的代码前提本轮已经具备。
