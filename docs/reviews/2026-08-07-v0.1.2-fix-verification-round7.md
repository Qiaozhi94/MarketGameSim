`_check_kpi006`，都会被误判为 KPI-006 违规**——修复绕过漏洞的同时，暴露了一个之前被
宽松校验掩盖的独立 bug。全仓库 830 个测试没有一个把 `verify_log` 接到走完整清算流程的

## 2. §1.8 残留绕过——确认已修复，新增对称验证，但发现新 bug

### 2.1 绕过反例2 确认已修复，且 LIQUIDATION 对称分支同样正确

`_check_kpi006` 现在对 AGENT 和 LIQUIDATION 两个分支都新增了
`if not decision_ids/mc_ids: return "..."` 的空集合判定。独立构造 5 组全新场景验证：

| 场景 | 结果 |
|---|---|
| AGENT 订单存在，零 `AGENT_DECIDE` | 正确判定失败 |
| **LIQUIDATION 订单存在，零 `MARGIN_CALL`（此前未测过的对称分支）** | **正确判定失败** |
| 正常场景（真实链接） | 正确通过 |
| AGENT 多数悬空+1正确 | 正确判定失败 |
| LIQUIDATION 多数悬空+1正确（对称） | 正确判定失败 |

`tests/unit/test_verify.py::TestKpi006Regression::
test_agent_orders_with_zero_decide_events_is_rejected` 的 `xfail` 标记确认已移除，
测试真实通过。链条深度仍未加深（只核对 `decision_event_id` 一跳），KPI-009 仍未接入
`verify.py`（这两点与第六轮一致，非本轮新增问题）。

### 2.2 新发现：LIQUIDATION 分支的 `decision_event_id` 引用错误，会导致真实清算日志被误判违规

用真实 `_run_post_batch_risk_check` 触发的完整强平流程（基于
`test_liquidation_stale.py` 同款账户走真实 `match_order` 管线，非手搭日志）复现：

```
MARGIN_CALL 自己的真实 event_id = e4_2
自动排程的 LIQUIDATION 订单的 decision_event_id = e4_0   ← 不等于 e4_2
```

**复核者独立重新验证**（不同的账户配置，直接调用 `_check_kpi006` 处理真实产出的隔离
事件子集）：

```
MARGIN_CALL   event_id=e4_2  decision_event_id=None       verdict=PENDING_LIQUIDATION
ORDER_ARRIVAL order_id=liq-A-4  event_id=e5_0  decision_event_id=e4_0  origin=LIQUIDATION

_check_kpi006(...) -> "LIQUIDATION order liq-A-4 missing MC e4_0"
```

**根因**：`matching.py`（约 758 行）`"decision_event_id": mc.caused_by_event_id`，而
`mc.caused_by_event_id` 恒为触发本次批处理的 `ORDER_ARRIVAL` 的 event_id
（`f"e{txn}_0"`），不是 `MARGIN_CALL` 自己的 event_id（`MARGIN_CALL` 作为该事务的副作用
记录，`record_index` 必然 ≥1，本例是 `_2`）。`docs/contracts/event-schema.md` 冻结的
契约要求 `ORDER_ARRIVAL.decision_event_id` 指向触发它的那条 `MARGIN_CALL` 本身，当前
实现**总是**指向 MARGIN_CALL 的触发源而非 MARGIN_CALL 本身——这是结构性错误，对任何
真实触发清算的实验日志都会复现，不是边界情况。

**含义**：§1.8 的绕过漏洞修复是正确且必要的，但它同时让这个此前被"宽松校验"掩盖的
独立 bug 浮出水面——严格版 `_check_kpi006` 现在会把任何含真实强平的合法日志判定为
KPI-006 违规。全仓库 `grep verify_log tests/` 只有 `tests/unit/test_verify.py` 一处，
没有任何测试把 `verify_log` 接到走完整清算流程的真实实验日志上，所以这个问题完全没有
被现有 830 个测试捕获。**这应作为下一轮的最高优先级**——比"哪条绕过路径没堵上"更
紧迫，因为它意味着 KPI-006 验证器现在对真实业务场景不可用。

## 3. 本轮确认的其他真实修复

### 3.1 §2.8 T503 PnL 桥接——确认已修复（非本轮任务直接要求，复核中意外发现）

`runner.py` 新增 `from market_game_sim.metrics.bridge import bridge_trade` 与
`_verify_bridge_residuals(events)` 函数，在 `run_one()` 内对每次真实运行调用，遍历所有
`TRADE_SETTLE` 的 `TRADE_POSTING`，用真实的 `valuation_mark_before_half_ticks`/
`valuation_mark_after_half_ticks`/`price_ticks`/`position_after_units` 字段计算残差并
`assert result["residual"] == 0`。核对这些字段确由 `matching.py` 真实写入（非
`.get(..., 0)` 兜底），830 个测试全过（含产生真实 `TRADE_SETTLE` 的场景）未触发该
assert 失败，证明该桥接校验被真实执行且通过。**判定：已修复，不再是孤儿模块**——但
桥接分量仅用作内部不变量断言，未写入 `build_study_report` 的报告输出，也未接入
`verify.py`（即 KPI-009 仍不满足"独立验证器一并断言"的要求，见 §2.1）。

### 3.2 §1.5 momentum 因子时间戳硬编码——已修复

`_record_trade_history` 现在写入真实 `event["timestamp"]`，不再是字面量 `0`。此前
momentum 恒为 0 是因为所有成交落入同一个 `bar_idx=0`（`_bars_from_history` 要求
`len(bars)>=6`，而全部成交时间戳相同导致只能产出 1 根 bar）。修复后只要模拟时长跨越
足够多个 60 秒 bar，momentum 理论上不再恒为 0（herding 此前已确认真接入，本轮无
回退）。Dirichlet 权重合成仍未接入（`weights=[0.2]*5` 字面量未变）。

### 3.3 §2.15 做市商维持保证金分支——有新代码但仍未接通

`strategy.py::market_maker_intents` 的签名与算法维持第四轮已有状态；本轮确认
`handler.py::_market_maker_intents` 调用处**仍未传入** `margin_ratio_bp`/`maint_bp`，
尽管 `iset["margin_ratio_bp"]` 已经计算好。判定维持"部分修复，未接线"。

### 3.4 §2.6 `endpoint_samples`——轻微进展

`build_study_report` 现在把 `len(endpoint_samples)` 写入报告输出的
`"n_endpoint_samples"` 字段，不再是完全零使用的死变量，但样本内部的
`margin_ratio_bp`/`leverage_bp` 数值本身仍未参与任何统计分析。

## 7. 建议

1. **`decision_event_id` 引用错误（§2.1新发现）是当前最高优先级**——`matching.py`
   自动排程强平单时应该用 `MARGIN_CALL` 自己的 event_id（`f"e{txn}_{mc_record_index}"`）
   而不是 `mc.caused_by_event_id`。修复后应该用一个真实触发过强平的完整实验日志跑一遍
   `verify_log`，确认不再被误判为 KPI-006 违规——这应该成为一个新的集成测试，永久锁定
   "真实清算日志必须能通过独立验证器"这条底线。
2. **KPI-009 需要接入 `verify.py`**（而不是留在 `runner.py` 内部断言），否则 E7 明文
   要求的"同一次验证一并断言"条款无法满足，即使因果链覆盖问题全部解决也不够。
3. **`_check_kpi006` 的链条深度仍需加深**，核对 `observation_event_id`/
   `information_set`/`market_data_event_id`（AGENT 分支）与
   `risk_mark_event_id`/`chain_id`/`chain_depth`（LIQUIDATION 分支）。
4. 打通 §1.7 真实配对结构、§2.7 Phase 6 统计口径——这两项已经连续七轮零进展，建议
   下一轮明确排期为独立任务，而不是继续被其他方向挤占。
5. §2.15（做市商维持保证金分支接线）只差一行调用参数，建议顺手处理。
6. 补齐 §3.2 的 Case 8/Case 9 测试——§1.9 核心逻辑与残留缺口都已修复，现在是补测试
   锁定行为的好时机。
