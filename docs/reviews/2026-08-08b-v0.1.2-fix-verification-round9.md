## 0. 结论先行

**"所有问题都修复完成"第九次仍不成立。** 本轮唯一的实质性代码变化是新增集成测试
`tests/integration/test_verify_liquidation.py`（落实了第七、八轮反复建议的
"§1.11 集成测试"）和 `_verify_bridge_residuals` 的 docstring 说明。**除此之外，
全部指标层、代理层、账本层此前标记"未修复"的条目本轮零变化**——`metrics/`、
`experiment/runner.py`（除新增函数说明外）、`agent/handler.py`、`agent/strategy.py`
的源码与第八轮逐字节/逐行一致。

**本轮最重要的发现是一次"元级别"的验证**：CLAUDE.md 新增的"每次修复必须补充配套
回归测试"规则，与本轮唯一的新代码改动几乎同时落地，这提供了一个天然的实践检验
机会——**结果是新规则的四条硬性要求里，本轮新增的测试只满足了 1 条**（显式说明
降级原因），另外 2 条被直接违反（正反场景都要断言、多账户批量场景要有专属测试），
1 条本该适用却未适用（`bridge_trade` 的已知精度缺口应该用 `xfail(strict=True)`
锁定，但完全没有测试覆盖它）。规则写下的同一轮，规则自己点名的反面教材
（`_verify_bridge_residuals` 降级）就没有被规则要求的方式处理。

同时确认了一个此前被忽略的真实 bug：**`bridge_trade` 的 MULT（cash-unit 缩放因子）
精度缺口是真实存在的，且触发范围是"任何有手续费或价格冲击的成交"，不是罕见边界
情况**——已用真实撮合场景实测触发（残差达 5,000,000 cash units 量级，不是舍入
噪声）。

## 1. §1.11 集成测试——流程扎实、能捕获真实回归，但违反新规则"批量场景"要求

`tests/integration/test_verify_liquidation.py::test_real_liquidation_log_passes_verify`：

  `_run_post_batch_risk_check`自动排程LIQUIDATION订单→该订单实际到达成交→写入
  临时jsonl→`verify_log()`端到端校验的全链路，不是手搭数据。
- **故障注入验证（已执行并撤销）**：把 `matching.py` 的
  `"decision_event_id": mc_event_id` 临时改回第七轮的错误写法
  `mc.caused_by_event_id`，运行该测试：
  ```
  FAILED ... AssertionError: verify failed: {'success': False, 'error': 'TI-5',
  'detail': 'KPI-006: LIQUIDATION order liq-A-4 missing MC e4_0'}
  ```
  确认测试**真的能捕获**这类回归，不是一个"总是通过"的假测试。随后立即恢复原状，
  `git diff` 确认 `matching.py` 无残留改动，全量 `pytest -q` 仍 831 passed。
- **违反新规则第③条**：该文件、以及仓库里其他所有涉及 `PENDING_LIQUIDATION` 的
  测试文件，都只构造了**单一**被强平账户。`ledger/risk.py::run_phase2_margin_scan`
  是对全部账户的批量扫描——正是新规则第③条点名的"强平批量扫描"类型逻辑，第八轮
  报告原文也强调"用此前七轮从未测过的多账户同批触发强平场景独立复现验证"才发现了
  §1.11 的 bug，但本轮补的回归测试**没有覆盖这个批量维度**。复核者自行构造了一个
  双账户同批穿仓的沙盒脚本，实测当前代码能正确处理（无活跃 bug），但仓库里没有
  任何测试锁定这一行为，一旦有人改坏索引对齐逻辑，CI 不会察觉。

**判定**：测试本身质量合格（真测试、能捕获回归），但不完整——只覆盖了单账户场景，
不符合刚写入的项目规则。

## 2. `bridge_trade` MULT 精度缺口——确认真实存在，触发范围广于预期

- **代码定位**：`metrics/bridge.py:29-31`，`spread`/`impact`/`revaluation` 全部用
  未乘 `MULT` 的原始 tick 值计算，而 `equity_delta = wallet_delta_units` 是全额
  cash-unit（含 `MULT=1000` 缩放）——两者量纲不一致。
- **docstring 的"已由 acceptance vectors 独立验证"说法有误导性**：
  `test_acceptance_vectors.py::_replay_check` 确实做了桥接残差验证，但它是**另起
  炉灶的独立实现**，显式用了 `MULT_HALF = MULT // 2` 把 MULT 正确计入——它验证的
  是"桥接分解公式在正确处理 MULT 后成立"，而**从未调用**生产代码里真正有 bug 的
  `bridge_trade()`。全仓库没有任何测试 import 或调用这个函数。
- **实测触发**（真实撮合场景）：零手续费+成交价恰好等于估值锚价的开仓成交，残差
  恰好为 0（两边碰巧同时退化，不代表量纲对齐）；加入 `taker_bps=10` 手续费后，
  实际触发：
  ```
  PnL bridge residual 5000000 != 0 for t6_0
  PnL bridge residual -5000000 != 0 for t6_0
  ```
- **影响范围**：任何存在手续费或估值锚价发生移动（价格冲击）的成交都会触发——这
  在真实市场模拟中是常态而非边界情况，残差量级与手续费/冲击量级同阶，不是舍入
  噪声。
- **违反新规则第②条**：docstring 已如实说明降级原因（符合第④条），但没有任何
  测试（无论 `xfail` 还是普通断言）覆盖 `bridge_trade` 本身，这个已知精度 gap
  完全没有仓库内回归保护。

## 7. 建议

1. **补齐 `test_verify_liquidation.py` 的多账户同批场景**——不需要新建文件，在
   现有测试基础上增加第二个测试函数，构造 2-3 个账户同批触发强平，验证
   `decision_event_id` 索引对齐在批量场景下依然正确。
2. **`bridge_trade` 的 MULT 精度缺口需要至少补一个 `xfail(strict=True)` 测试**
   锁定当前行为（残差非零、触发 warning），防止这个已知缺口在未来被无声地进一步
   恶化或被误认为"已经处理好"。长期应该修复 `bridge_trade` 本身把 MULT 计入公式。
3. **§2.15 需要补齐正反两个测试用例**（`margin_ratio_bp` 低于 `maint_bp` 时只挂
   减仓方向 / 高于时正常双边报价），这是连续两轮被点名、且新规则专门针对的缺口，
   工作量不大，建议优先处理。
4. **CLAUDE.md 新规则需要一次自查**——建议下一轮修复前，先确认这条规则本身被
   理解和执行到位，而不是只在"写文档"这一步完成、在"写代码"这一步被绕过。规则
   的价值取决于是否被遵守，不取决于是否被记录。
5. 其余建议维持第八轮 §7 的优先顺序（KPI-009 接入 `verify.py`、链条深度加深、
   §1.7/§2.7 配对与统计口径、Case 8/9 测试、`risk.py`/`metrics` 专属单测等）。
