## 2. 发现与修复

### 2.1 CI 覆盖率阈值仍是 87%（T001b 遗留一半未做）

`.github/workflows/ci.yml` 的 `--cov-fail-under` 实测仍是 87，但 T001b 早就
声称"补测试使覆盖率达 90%，并将 CI 阈值提升到 90"。本地实测 book+ledger
合并分支覆盖率 91%，确认可以安全提升，已改为 `--cov-fail-under=90`。

### 2.2 T701-T703：BENCH-001 基准从未真正跑起来过

`tests/simulation/` 是空目录，`BENCH-001.yaml` 的 `book_operations_golden`
仍是 `null`（"首次实现后写入"占位符从未填）——覆盖断言、CALIB-001 校准、
`book_operations` 计数器全部不存在。

新增 `market_game_sim.bench` 包：`population.py`（从解析后的配置按
`leverage_tier_distribution`/`aggressiveness` 分布逐代理确定性抽样展开成
190 个 `AgentSpec`）、`calib.py`（CALIB-001 微基准）、`coverage.py`（五项
覆盖断言）、`runner.py`（桥接执行）、`__main__.py`（CLI 入口）。
`book/orderbook.py` 新增 `operation_count` 计数器（README §2 第二层硬件
无关回归断言的载体）。

**正式标定（锁 CPU 亲和性到 P 核 + 高性能电源计划 + 5 次取中位数）本轮
做不到锁核这一步**（Meteor Lake 的 P/E 核逻辑处理器排列不保证顺序，无法
可靠判断），已与用户确认：先实现代码+测试，`book_operations_golden` 和
`reference-machine.md` 的 CALIB-001 参考耗时不冻结，留待具备条件时单独
标定——写错的 golden 数字比不写更糟。

### 2.3 意外发现：代理策略 §6.2 全撤重报从未实现（本轮最严重的发现）

为验证 T701 的覆盖断言，真实跑一次 100k 事务的完整 BENCH-001，产出
**0 撤单 / 0 强平 / 0 部分成交**。深挖根因：`docs/contracts/agent-strategy.md`
§6.2 明确要求"每次决策先撤销自己全部未成交挂单，再按规则重新下单"（信念
代理与做市商共享），但 `agent/handler.py`/`agent/strategy.py` 里从未有任何
代码产出过 CANCEL 动作——全仓库搜索 `action.*CANCEL` 在代理层为零命中。

`_handle_cancel`（`book/matching.py`）撤单处理本身早就实现且有专属单测，
但没有任何调用方真正通过 `match_order` 把一个代理发起的 CANCEL 事件送
进去过。修复：

- `agent/handler.py` 新增 `_cancel_stale_orders`，在 `handle_agent_decide`
  构建新订单前，为该代理 `active_orders_by_agent` 里全部在簿挂单各发一条
  CANCEL 类 `ORDER_ARRIVAL`，必须先于新订单入队（同一 (timestamp,class) 下
  按入队顺序处理，否则新订单的保证金准入检查会看到尚未释放的旧挂单占用）；
- `book/matching.py::_populate_r0_defaults` 发现并修复一个关联 bug：该函数
  对所有 `ORDER_ARRIVAL`（含 CANCEL）无条件跑 SUBMIT 专用的预撮合/保证金
  预估逻辑，在 `quantity_units` 为 null（CANCEL 的规范取值）时抛
  `TypeError`——这条路径此前从未被实际执行过的撤单请求触发过。

修复后 5000 事务小规模基准从 0 撤单变为 1122 撤单；100k 事务完整规模基准
撤单数变为 28482，**耗时从 198 秒降至 6 秒**（陈旧挂单堆积此前是撮合性能
的主要拖累，副作用式验证了修复的必要性）。但强平/连锁强平/部分成交三项
仍为 0——190 代理在 100k 事务内的价格波动/杠杆敞口不足以触发保证金判定，
属于 README §4 step 3-4 定义的"参与者构成或 `max_transactions` 需要调整"
的标定范畴，不是新的实现缺陷，E5/E6 因此仍不勾选。

### 2.4 T704：跨进程确定性从未验证过

CI 工作流自己的注释承认这一步没做："真正的确定性门必须跨两个不同 seed 的
独立进程比较同一运行的事件摘要...由 0.1.1 T602/退出条件 E4 负责"，但全
仓库搜不到任何实现。新增 `tools/determinism_probe.py`（固定双种子实验，
输出 blake2b 事件摘要+样本分类+强平指标+完整 study report 的 JSON）+
`tests/integration/test_cross_process_determinism.py`（两个不同
`PYTHONHASHSEED` 的真实子进程比较，故障注入验证——临时换成内置 `hash()`
后测试如预期捕获跨进程不一致）。

### 2.5 E1：验收案例 7 从未有专属测试

`test_acceptance_vectors.py` 只覆盖了案例 1-6、7b、8、9、10 共九项，
`acceptance-vectors.md` §3 明确的案例 7（价格驱动的强平数量重算：
288.678→193.271，差异来自 `risk_mark` 94→92 变化而非部分成交本身）从未
有专属测试——案例 8 涉及类似流程但只做"第二次 `required_quantity` 大于
第一次"的宽松断言。驱动真实内核/撮合/风控扫描全流程复现文档场景，实测
结果与文档表格逐项吻合，确认底层实现本身没有 bug，只是从未被锁定。

### 2.6 E3：配置哈希追溯机制不存在

`experiment/` 包内从未计算过任何配置哈希——`eventlog/writer.py` 虽支持
`RUN_HEADER` 携带调用方传入的 `config_hash`，但没有调用方真正算过。新增
`experiment/config.py::compute_config_hash`（blake2b，非内置 `hash()`），
接入 `run_paired` 的 `comparison` 返回值。

### 2.7 E4：`build_continuous_part` 低样本量警告分支无专属测试

Part 2（`build_continuous_part`）的 >30% 空值警告分支只被间接跑过，覆盖率
98%、缺 2 个分支。补齐 4 个测试。

### 2.8 E7：核查确认已达标，未做修改

`run_one` 无条件调用 `_verify_bridge_residuals`（硬 `assert`，KPI-009）和
`check_causal_references`（KPI-006，结果影响 `classify_run` 的 TI-1 分类）
——不是验收向量测试专属路径，每次真实运行都执行。
