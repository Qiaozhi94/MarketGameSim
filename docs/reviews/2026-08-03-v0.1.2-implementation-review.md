### 1.11 强平单 `decision_event_id` 引用错误，导致真实清算日志被 KPI-006 验证器误判违规 【已修复 · 第8轮，含多账户场景验证】

- **位置**：`src/market_game_sim/book/matching.py`（约 758 行，自动排程 LIQUIDATION
  订单处）：`"decision_event_id": mc.caused_by_event_id`。
- **背景**：§1.8 的两条 `_check_kpi006` 绕过路径本轮被彻底修复后（见 §1.8），复核者
  按惯例用一次真实触发清算的完整流程（走 `_run_post_batch_risk_check` →
  `match_order`，不是手搭日志）来验证严格版校验器是否对合法日志仍然放行，结果发现
  **合法日志本身就无法通过**。
- **实测复现**：
  ```
  MARGIN_CALL 自己的真实 event_id       = e4_2
  自动排程的 LIQUIDATION 订单的 decision_event_id = e4_0   ← 不等于 e4_2

  _check_kpi006(真实产出的隔离事件子集) ->
      "LIQUIDATION order liq-A-4 missing MC e4_0"
  ```
  复核者独立用不同账户配置重新验证，结果一致。
- **根因**：`mc.caused_by_event_id` 恒为触发本次批处理的 `ORDER_ARRIVAL` 的 event_id
  （`f"e{txn}_0"`），不是 `MARGIN_CALL` 自己的 event_id（`MARGIN_CALL` 作为该事务的
  副作用记录，`record_index` 必然 ≥1，本例是 `_2`）。
- **违反**：`docs/contracts/event-schema.md` 冻结的契约要求
  `ORDER_ARRIVAL.decision_event_id`（LIQUIDATION 分支）指向触发它的那条 `MARGIN_CALL`
  本身——当前实现**总是**指向 `MARGIN_CALL` 的触发源而非 `MARGIN_CALL` 本身，这是
  结构性错误（由 `caused_by_event_id` 的语义决定），不是偶发场景问题，对**任何**真实
  触发过强平的实验日志都会复现。
- **含义**：§1.8 的绕过漏洞修复是正确且必要的，但它同时让这个此前被"宽松校验"掩盖的
  独立 bug 浮出水面——严格版 `_check_kpi006` 现在会把任何含真实强平的合法日志判定为
  KPI-006 违规。全仓库 `grep verify_log tests/` 只有 `tests/unit/test_verify.py` 一处，
  没有任何测试把 `verify_log` 接到走完整清算流程的真实实验日志上，所以这个问题完全
  没有被现有 830 个测试捕获。**这是当前最高优先级**——比"链条深度不够"或"KPI-009
  未接入"更紧迫，因为它意味着 KPI-006 验证器现在对真实业务场景不可用，且没有任何
  回归测试保护。
- **修复思路**：自动排程强平单时应该用 `MARGIN_CALL` 自己的 event_id
  （`f"e{txn}_{mc_record_index}"`）而不是 `mc.caused_by_event_id`。修复后应新增一个

  没有任何地方读取消费。`experiment/runner.py::run_one` 改为手工预排
  `for cycle in range(3)` 三轮观察，硬编码轮数——代理不会持续参与市场，这与
  "确定性事件驱动、代理持续观察决策"的模型假设不符。
- **第2/3/4轮复核**：`pending_reschedules` 仍只有写入点，`runner.py` 仍硬编码
  3 轮，四轮零进展。
- **第5轮复核（本轮最值得警惕的发现）**：`runner.py` 新增消费端 `_flush_reschedules`，
  并在 `kernel.run(...)` **返回之后**调用：
  ```python
  kernel.run(_dispatch_agents, world, max_transactions=config.max_transactions)
  _flush_reschedules(world, kernel)
  ```
  ```python
  def _flush_reschedules(world, kernel):
      if kernel.terminated is not None:
          return
      ...
  ```
  **这个 guard 条件必然为真，函数每次调用都是空操作**：`kernel/runner.py::run()` 无论
  正常耗尽队列、达到 `max_transactions`，还是抛异常，返回前 `self._terminated` 一定
  已被赋值（不再是 `None`）。而 `_flush_reschedules` 是在 `run()` 返回**之后**才被
  调用，此时 `kernel.terminated` 已经不可能是 `None`，guard 100% 命中，函数体从未被
  执行到。即便去掉 guard，此时 `kernel.run()` 已退出，也没有后续调用去消费新入队的
  事件——结构上是双重失效。**实测验证**：构造真实 `run_one` 调用
  （`observe_interval_ns=1_000_000`），观察轮数固定为 3（`[0, 1000000, 2000000]`），
  与硬编码 `for cycle in range(3)` 完全吻合。**这不是"零改动"，是"改了但没用"**——
  比零进展更需要警惕，因为表面上像是接上了消费端，静态审查如果不追踪调用时机会误判
  为已修复。建议下一轮修复时把消费逻辑挪到 `kernel.run()` 内部循环中、每次事务提交后
  检查并消费，而不是在整个 `run()` 结束后才调用。
- **第6轮复核**：`runner.py` 把观察预排上限从"硬编码 3 轮"改为"硬编码预排最多 100

  观察超过 100 轮或超过 1 万秒，或 `observe_interval_ns` 配置得比预排步长更密，机制
  依然会断线——只是断线阈值被推高，没有任何测试验证超出预排范围会发生什么。

   `information_set`/`market_data_event_id`（AGENT 分支）与
   `risk_mark_event_id`/`chain_id`/`chain_depth`（LIQUIDATION 分支）。

   的静态预排掩盖症状，应挪到 `kernel.run()` 内部循环中按需消费 `pending_reschedules`。
