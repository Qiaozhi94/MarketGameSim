## 3. 部分进展 / 新发现的隐蔽问题

### 3.1 §1.5 代理决策管线——reversion 真接入，momentum/herding 是"伪接入"

`handler.py` 不再对 momentum/reversion/herding 使用字面量 `Decimal("0")`，改为：
```python
history = world.get("trade_history", {}).get(spec.agent_id, [])
bars = _bars_from_history(history, bar_ns=60_000_000_000)
mf = momentum_factor(bars, lookback=5)
rf = reversion_factor(info.last_ticks, iset.get("initial_price_ticks", 10000))
hf = herding_factor(bars)
```

- **reversion 是真实修复**：直接读 `iset["last_ticks"]`（真实成交/book 数据）。
- **momentum/herding 实际仍恒为 0**：`world["trade_history"]` 在 `runner.py` 初始化为 `{}`
  后，全仓库没有任何写入点——没有任何地方在成交后往里 append 数据。`history` 永远是
  `[]`，`bars` 永远是 `[]`，`momentum()`/`herding()` 在 `bars` 不足时返回 `_ZERO`。**换了
  写法但运行时行为和硬编码 0 完全等价**——问题从"字面量硬编码"变成了"上游数据管道缺失"，
  同样的最终效果，更难被静态审查发现（代码看起来"调用了真实因子函数"）。
- 权重合成仍硬编码 `[Decimal("0.2")]*5`，`dirichlet_draw` 生产路径零调用，未变。

### 3.2 §2.14 K 线聚合——新增时间戳字段但仍是死代码，且新代码本身有边界 bug

`Trade` 新增 `timestamp: int = 0`，`aggregate_bars` 改为
`tr.timestamp // bar_ns if tr.timestamp else now_ns // bar_ns`。

**独立验证确认存在真实边界缺陷**：`if tr.timestamp` 用真值判断而非 `is not None`，无法
区分"时间戳合法地等于 0"（如仿真时间原点的第一笔成交）与"时间戳未设置"。实测构造
`Trade(timestamp=0, ...)` 传入 `aggregate_bars(bar_ns=60e9, now_ns=999e9)`，该笔成交被错误
分到 `bar_idx=16` 而不是应有的 `bar_idx=0`。

且生产路径根本不走这个函数——`handler.py` 有一份**完全独立、重复实现**的
`_bars_from_history()`，用 dict 而非 `Trade` dataclass，逻辑相似但是另一套代码，同样受
§3.1 提到的 `trade_history` 空数据管道拖累。`aggregate_bars` 依旧零调用点，是死代码。

### 3.3 §2.16 代理续观察调度——新增代码但结构上保证不会执行（本轮最值得警惕的发现）

`runner.py` 新增消费端 `_flush_reschedules`，并在 `kernel.run(...)` **返回之后**调用：
```python
kernel.run(_dispatch_agents, world, max_transactions=config.max_transactions)
_flush_reschedules(world, kernel)
```
```python
def _flush_reschedules(world, kernel):
    if kernel.terminated is not None:
        return
    ...
```

**这个 guard 条件必然为真，函数每次调用都是空操作**：`kernel/runner.py::run()` 无论正常
耗尽队列、达到 `max_transactions`，还是抛异常，返回前 `self._terminated` 一定已被赋值
（不再是 `None`）。而 `_flush_reschedules` 是在 `run()` 返回**之后**才被调用，此时
`kernel.terminated` 已经不可能是 `None`，guard 100% 命中，函数体从未被执行到。即便去掉
guard，此时 `kernel.run()` 已退出，没有后续调用去消费新入队的事件——结构上是双重失效。

**实测验证**：构造真实 `run_one` 调用（`observe_interval_ns=1_000_000`,
`max_transactions=5000`），观察轮数固定为 3（`[0, 1000000, 2000000]`），与硬编码
`for cycle in range(3)` 完全吻合——续观察调度全程未起作用，与"仍硬编码 3 轮"效果完全一致。

**这不是"零改动"，是"改了但没用"**——比零进展更需要警惕，因为表面上看起来像是接上了
消费端，静态审查如果不追踪调用时机会误判为已修复。

## 7. 建议

1. **§1.9、§1.10、§1.8 已连续五轮被列为最高优先级，建议下一轮修复前先专门确认这三项
   被安排进了具体的修复任务**，而不是继续被其他方向的改动挤占——五轮里这三项从未被
   触碰过一次实质性的代码改动。
2. **§2.16 的 `_flush_reschedules` 需要修正调用时机**（应在 `kernel.run()` 内部循环中、
   每次事务提交后检查并消费 `pending_reschedules`，而不是在整个 `run()` 结束后才调用），
   并补一个能验证"代理持续观察超过硬编码轮数"的集成测试，防止这类"结构上不可能执行"的
   代码再次被误判为修复。
3. **§1.5/§2.14 依赖的 `world["trade_history"]` 数据管道需要补上写入点**——否则 momentum/
   herding 因子和 `_bars_from_history`/`aggregate_bars` 无论怎么改都会因为拿不到数据而
   继续实质性空转。同时 §2.14 的 `if tr.timestamp else` 边界 bug 建议顺手改成
   `is not None` 判断。
4. **本轮两项真实修复（§2.3、§2.5）建议尽快补上专属单测**，防止后续改动无意中回退——
   五轮下来测试总数几乎没有随生产代码改动同步增长，是需要关注的系统性问题。
5. 在 §1.8、§1.9、§1.10 解决之前，仍不建议宣布 E1–E7 达成。
