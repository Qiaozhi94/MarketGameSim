独立复跑 D019 与 D014 相邻回归 8 passed，轮末唯一门禁 2256 passed。

**闭环证据**：`6232cdb` 推送后 CI run [33644101359] 四个 job 全绿——真源与生命周期校验、
ruff、pytest 3.11、pytest 3.13。19 条发现全部 fixed，未决 Critical/High/Medium/Low = 0/0/0/0。

**模式教训**：规则与工作流必须成对修改；两个正则解析同一语法时必须共用家族与分隔口径；
声明前缀采集器与 registry 完整声明解析器的分隔约束不能互相移植；删除范围锚点前必须验证
完整性门禁仍非空转；CURRENT 与 FIX-log 均属于过程稿，忽略与验证排除应同步落地。

**变异探测本身会假阴性**：round 2 首次验证 UX 门禁时，检视人把需求声明行与 AC 引用行
一起替换、又只删了两处 UX-202 引用中的一处，两次都得到"静默通过"的错误结论，收紧变异后
才确认门禁其实是响的。构造变异输入时必须确认**只改被测的那一面**，否则会把好门禁误判成
空转门——这与门禁真的空转，在输出上完全一样。

**`pipe-swallows-exit-code` 第二次复发**：循环 11 记过「门禁命令不能接在管道后面」，本轮
检视人仍用 `python tools/verify.py 2>&1 | tail -15` 跑唯一门禁。后果不是误判通过（verify.py
自己打印了失败步骤），而是**证据丢失**：pytest 的失败详情被 tail 截掉，那一次红无法归因。
随后两次完整重跑（2256 passed / 2256 passed）与 CI 两个 pytest job 均绿，该次失败归档为
不可复现。教训升级为：门禁命令一律裸跑或写文件，`tail`/`head` 只用于事后读文件。

**复核结论的署名必须属于复核人**：`FIX-log.md` 里出现了一条以 `[review-r4]` 署名、声称
"复核人重跑 verify.py 全绿"的记录，但它由修复者写入，不是检视人产出。结论巧合一致不改变
性质——`self-approved-closure` 的判据是"写结论的人和执行修复的人是否同一个"，署名代写会让
这个判据失效。复核结论只以 `CURRENT-<type>.md` 与本文件中检视人写下的内容为准。
