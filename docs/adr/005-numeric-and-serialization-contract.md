# ADR-005：数值表示、舍入与序列化口径

日期：2026-07-30  
状态：Accepted  
关联规格：[`../../specs/001-market-simulation-foundation/spec.md`](../../specs/001-market-simulation-foundation/spec.md)  
解决问题：PRD Q-011  
关联文档：[指标字典](../product/metrics-dictionary.md)、
[事件 Schema](../../specs/001-market-simulation-foundation/event-schema.md)、
[退化状态定义](../../specs/001-market-simulation-foundation/degenerate-states.md)

## 背景

价格已由 KR-003 与指标字典 §1.7 规定为整数 tick 计数，但**数量、现金、名义金额、
maker / taker 手续费、返佣与已实现 PnL 没有规定数值表示与舍入方向**。

`benchmarks/BENCH-001.yaml` 使用 `tick_size: 0.01`、`min_quantity: 0.001`、
`maker_bps: -1.0`、`taker_bps: 5.0`。若实现直接以二进制浮点承载这些量：

- 指标字典 §5 要求「**每个事件之后**」现金与库存守恒等式严格成立，浮点累加的舍入
  误差会使该断言在长运行下必然失败，而失败点与配置相关、不可复现地漂移；
- 负 maker 费率意味着交易所向代理**付钱**，舍入方向若与 taker 费相同，累计费用可能
  为负，守恒等式第一条右侧不再是常数；
- 手续费预冻结（degenerate-states §3.2）依赖「最大可能手续费」可精确计算，浮点下
  「恰好够」的边界订单会随机被拒或使现金为负，违反 FR-003；
- NFR-001 的逐事件一致性在跨平台浮点行为差异下不再有保证。

这些是订单准入、费用预冻结、账户不为负与 KPI-001 守恒验收的共同基础。留到编码时
临时决定，不同模块极易采用不同口径。

此外，事件日志的缺失值表示存在跨文档冲突：FR-012 要求不得产出 NaN，而事件 Schema
§4.3 与指标字典 §3.1 要求未定义报价记为 NaN；而 JSON 标准不支持 NaN 字面量，直接
写入 JSONL 会产出非标准数据或序列化失败（plan.md 的输出格式为 JSONL / Parquet）。

## 决策

### 1. 一切金额与数量以最小单位整数承载

领域层与事件日志中，下列量**均为 Python `int`**，不得出现 `float`：

| 量 | 内部表示 | 单位定义 |
|---|---|---|
| 价格 | `price_ticks` | `tick_size` |
| 数量 | `quantity_units` | `min_quantity` |
| 现金、名义金额、费用、返佣 | `*_cash_units` | `cash_unit` |
| 持仓成本 | `cost_cash_units` | `cash_unit` |

`cash_unit` 为新增的必填市场配置项，**初值 `1e-8`**（名义计价货币的最小结算单位）。

### 2. 配置解析规则

- 配置文件中的十进制值一律以字符串形式读取后用 `decimal.Decimal` 解析，**禁止经过
  `float` 中转**。为使该规则在 YAML 层面可执行，**所有非整数数值必须写成带引号的
  字符串**（`tick_size: "0.01"`、`cash_unit: "1e-8"`），否则 `yaml.safe_load` 会
  直接产出 `float`，合同在解析的第一步就已失效。整数字面量（计数、纳秒时长、种子）
  无精度问题，照常书写。该约定覆盖**领域量**（价格、数量、金额、费率、库存上限、
  报价规模）；不参与领域运算的测量阈值（如 `normalized_wall_seconds_max` 这类墙钟
  秒数）不适用，照常写浮点；
- 配置校验须断言这些字段在解析前确为字符串——**收到 `float` 即报错**，不接受
  「先转 str 再转 Decimal」的补救，那等于默认了一次二进制舍入；
- 单位换算后必须为整数，否则配置校验失败并终止，不静默取整——与 degenerate-states
  §5「价格非 tick 整数倍即拒绝」同一理由；
- **配置校验必须断言 `tick_size × min_quantity` 是 `cash_unit` 的整数倍。** 该约束
  使名义金额 `price_ticks × quantity_units × (tick_size × min_quantity / cash_unit)`
  恒为整数，成交金额本身**不产生任何舍入**。BENCH-001 满足该约束
  （`0.01 × 0.001 = 1e-5 = 1000 × 1e-8`）。

### 3. 舍入只发生在费用一处，且方向固定

名义金额精确，因此**全系统唯一的舍入点是手续费**：

```text
fee_cash_units = round_away_from_agent(notional_cash_units × bps / 10000)
```

- **正费率（taker，或正的 maker 费率）向上取整**至 `cash_unit`（代理多付）；
- **负费率（maker 返佣）返还额向下取整**至 `cash_unit`（代理少收）；
- 两者合为一条规则：**舍入方向恒不利于代理、有利于交易所**。

理由：该方向保证「交易所累计费用」单调不减且非负，指标字典 §5 第一条守恒等式在
整数域内**精确**成立；同时保证按上界预冻结的费用永远够扣，代理现金不会因舍入
转负。反方向舍入则两条保证同时失效。

不可整除的余数由此归于交易所累计费用，无需另设余数账户。

### 4. 预冻结额

```text
冻结额 = 名义金额（按订单限价；市价单按可成交范围的最坏价格）
       + ceil(名义金额 × max(taker_bps, maker_bps, 0) / 10000)
```

实际成交为 maker 时，多冻结部分在 `TRADE_SETTLE` 结算时释放。费率为负时费用项按 0
计算，不得为负——预冻结是上界估计，不能因预期返佣而少冻结。

### 5. PnL 不引入新的舍入

- **已实现 PnL** 由整数现金流直接得出（卖出所得 − 对应持仓的整数累计成本），不单独
  计算均价；
- **持仓均价不作为状态存储**，只保留整数 `cost_cash_units` 与 `quantity_units`，
  均价仅在报告层按需计算，避免均价舍入回流进账本；
- **未实现 PnL** = `quantity_units × mark_price_cash_units − cost_cash_units`，
  `mark` 未定义时该值为缺失值（见 §6），不得以 0 代替。

### 6. 序列化：领域层无 NaN，输出层用 null

区分两个层次，消除 FR-012 与事件 Schema 的表述冲突：

- **领域状态层**：不存在 NaN。整数表示下 NaN 在语义上不可构造，FR-012 的「不得产出
  NaN」指的是这一层——不得出现未定义状态；
- **输出层**：未定义的量（单边簿下的 `mid`、无成交时的 `last`、`mark` 缺失时的未实现
  PnL）以**缺失值**表达。JSONL 写 `null`，Parquet 写 null；
- **分析层**：读取后由分析代码将 null 映射为 NaN 再做统计，指标字典的 NaN 表述仅在
  这一层有效。

### 7. Canonical serialization 纳入 schema 版本合同

事件日志的规范序列化规则随 `schema_version` 管理，变更须提升版本号：

- 数值字段一律为 JSON 整数字面量，**不得出现浮点字面量、指数记法或引号包裹的数字**；
- 缺失值一律为 `null`，不得使用 `NaN`、`Infinity`、空字符串或省略字段；
- 对象键按 UTF-8 码位升序排列；
- 单位元数据（`tick_size`、`min_quantity`、`cash_unit`）写入运行元数据头部一次，
  事件体内不重复携带。

KPI-002 的事件摘要哈希在此规范序列化之上计算，因而与语言、平台的浮点实现无关。

## 备选方案

- **方案 A：全程 `Decimal`**  
  优点：配置值可直读，无需单位换算。  
  缺点：仍需为每个运算点声明 context 与舍入方式，否则问题只是从「浮点误差」变成
  「上下文依赖」；性能远低于 `int`，与 NFR-003 的 10 秒门槛冲突；`Decimal` 的哈希与
  序列化表示不唯一（`1.0` 与 `1.00` 相等但表示不同），威胁 KPI-002。

- **方案 B：浮点 + 容差断言**  
  优点：实现最省事。  
  缺点：把守恒等式从**精确断言**降级为**容差断言**，KPI-001 失去意义；容差阈值本身
  会成为一个需要调参的隐藏变量。明确排除。

- **方案 C：最小单位整数（已采纳）**  
  优点：守恒等式在整数域精确成立；确定性与跨平台一致性天然满足；性能最优；序列化
  表示唯一。  
  缺点：需要一层单位换算与配置校验；报告层显示前须转回十进制；`cash_unit` 成为一个
  新的必填配置项，取值过粗会使费用舍入相对误差上升（1e-8 下可忽略）。

## 后果

- **正面**：KPI-001 的守恒断言可写成整数相等而非近似相等；NFR-001 的跨平台一致性
  不再依赖浮点行为；FR-012 与事件 Schema 的 NaN 冲突消解；负 maker 费率的返佣有了
  明确的精度与最小结算单位。
- **负面**：
  - 领域层与配置层之间多一层单位换算，实现与测试成本上升；
  - `cash_unit` 与 `tick_size × min_quantity` 的整除约束限制了配置自由度——不满足的
    参数组合会被配置校验直接拒绝，须在文档中显著说明；
  - 报告与回放层须自行还原十进制表示，回放器需读取运行元数据头部的单位定义。
- **后续行动**：见下节文档同步清单；配置校验与舍入方向须进入 T003 / T004c 的属性
  测试（不可整除的费用、恰好位于冻结边界的订单、负费率返佣）。
