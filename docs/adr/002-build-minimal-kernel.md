# ADR-002：自建最小仿真内核，不采用 ABIDES/PAMS 作为底座

日期：2026-07-29  
状态：Accepted  
关联规格：[`../../specs/002-belief-testing-laboratory/spec.md`](../../specs/002-belief-testing-laboratory/spec.md)  
解决问题：PRD Q-006

## 背景

多代理金融市场仿真已有成熟开源框架（如 ABIDES、PAMS 等）。需要决定 MVP 是在其中
之一上构建，还是自行实现最小内核。

约束来自宪章与已有需求：

- **宪章第 2 条**将撮合正确性定为不可妥协，账本守恒与订单生命周期必须由确定性测试覆盖；
- **宪章第 3 条**要求逐事件确定性与可复现；
- **NFR-004** 要求核心领域层不依赖 UI、数据库或机器学习框架。

## 决策

**MVP 自行实现最小仿真内核**，核心领域层仅使用 Python 标准库。

ABIDES、PAMS 等框架作为**设计参考**而非依赖：在 Phase 1 实现前先研读其事件内核、
延迟模型与代理调度设计，并使 FR-008 的事件日志 schema 保持在可导出为外部格式的
粒度上，为 M4 的潜在互操作留出路径。

外部框架的具体实现细节以其当前版本文档为准，本 ADR 不对其特性作事实性断言。

## 备选方案

- **方案 A：以 ABIDES/PAMS 为底座**  
  优点：免去撮合、调度、延迟模型的初始实现；已有社区验证与配套生态。  
  缺点：宪章第 2 条要求撮合正确性由本项目的确定性测试保证，这意味着无论是否复用，
  都必须自行审计其撮合与账本实现——而审计陌生代码库的成本通常高于实现一个价格
  时间优先订单簿（后者的主要工作量在测试，且测试无论如何都要自己写）。此外，
  这类框架的依赖栈（数值计算、RL 环境等）会被拉入核心层，与 NFR-004 冲突；其
  确定性与守恒保证的强度也未必达到本项目宪章要求的水平。

- **方案 B：自建最小内核（已采纳）**  
  优点：撮合与账本代码完全可控，宪章第 2、3 条的保证可以从设计层落实而非事后加固；
  核心层零第三方依赖，满足 NFR-004；代码规模小，修改成本低，便于快速试验新的
  市场机制与代理类型。  
  缺点：需自行实现并验证订单簿、事件内核与延迟模型；无法直接复用外部生态（如
  现成的 RL 训练环境）。

## 后果

- **正面**：撮合正确性、确定性和账本守恒成为自有代码的设计属性，宪章第 2 条可由
  测试直接证明；核心层保持轻量，易于修改和推理。
- **负面**：M1 需要投入实现订单簿与事件内核；若 M4 决定引入强化学习代理，无法直接
  复用外部框架的训练环境，需自行提供接口适配。
- **后续行动**：
  - `plan.md` 阶段 5 的"评审 ABIDES/PAMS 兼容或迁移"改为：仅在 M4 出现具体互操作
    需求（如复用外部 RL 环境）时重新立项，不作为默认计划项；
  - Phase 1 前完成对参考框架事件内核设计的调研记录；
  - 事件日志 schema 设计时保留导出适配的可能性。
