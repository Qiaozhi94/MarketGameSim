# ADR-002：同时间戳事件调度与因果链的强制表达

日期：2026-07-30  
状态：Accepted（2026-08-01 修订为 queue key / log key 双键）
关联规格：[`../../specs/v0.1-belief-testing-laboratory/spec.md`](../../specs/v0.1-belief-testing-laboratory/spec.md)  
解决问题：PRD Q-012  
关联决策：v0.1 规格 D-5（离散事件内核）  
关联文档：[事件 Schema](../contracts/event-schema.md)

## 背景

### 1. 全序键的单调性未被保证

修订前的 KR-003 曾定义事件全序键为 `(timestamp, priority_class, seq)`，event-schema §3 规定
「数值越小越先处理」。但事件是在处理其他事件的过程中产生的：

- `AGENT_DECIDE`（class 4）产生订单意图，形成 `ORDER_ARRIVAL`（class 0）；
- `TRADE_SETTLE`（class 1）触发 `MARKET_DATA_PUBLISH`（class 2）；
- `AGENT_OBSERVE`（class 3）触发同一代理的 `AGENT_DECIDE`（class 4）。

第一条链在通信延迟配置为 0 时会在**当前时间戳**上入队一个 class 0 事件，而当前正在
处理的是 class 4。新事件的全序键小于已弹出事件的键——事件队列不再单调，「同时间戳
下数值越小越先处理」在实现层无法成立。

这不是表述模糊，而是离散事件内核的**单调性被破坏**：一个逻辑上属于「过去」的事件
被插回队列。后果直接触及三项核心保证：

- **KR-003 的全序语义**：同一批事件的处理顺序取决于它们被产生的时机，而非其键；
- **NFR-v0.1 / KPI-002**：事件摘要哈希按全序逐个计算，顺序不确定则哈希不确定；
- **A-002**：代理可能观察到一个尚未处理完当前时间戳全部订单的簿状态。

### 2. 因果链没有被 Schema 强制表达

KPI-006 与 US-3 要求从任一成交追溯到代理观察、决策规则、订单与账户变化。现有 Schema
有观察、决策、订单、成交四类事件，但**没有显式的因果外键**：

- `ORDER_ARRIVAL` 不含决策标识，无法确定它来自哪一次 `AGENT_DECIDE`；
- `AGENT_DECIDE` 不含观察标识，无法确定它基于哪一次 `AGENT_OBSERVE` 的信息集；
- `intents` 列表的元素没有标识，一次决策产生多笔意图时（做市商双边报价即产生 2 笔）
  无法与后续订单一一对应；
- 撤单事件不关联其触发决策。

因此追溯链在 `order_id → decision` 一步断裂，只能靠「同代理、时间相近」启发式重建。
叠加 E-001 默认只记录 `information_set` 摘要，完整链路还依赖用当前代码重跑一次，
KPI-006 在展示层看似可用，却没有可机器验证的完整性。

## 决策

### 1. 队列调度键与事务日志键分离（KR-003 / KR-006）

2026-08-01 的撮合合同明确了一张订单是一个原子事务。原三元键不能同时表示“队列中谁
先弹出”和“一个事务内的记录必须紧跟父事件”，因此冻结为：

```text
queue_key = (timestamp, priority_class, enqueue_seq)
log_key   = (timestamp, transaction_seq, record_index)
```

`queue_key` 只用于队列事件；`transaction_seq` 在队列事件弹出时分配，父记录的
`record_index=0`，事务记录依实际发生顺序递增。日志、哈希、因果比较与重放只使用
`log_key`。

内核不变量：事务期间新入队的队列事件 `e'` 必须满足
`queue_key(e') > queue_key(current)`；事务内新记录必须满足 `record_index` 严格递增。
违反任一条件立即终止，不得静默重排。

推论：队列事件回到更小 class 时，`timestamp` 必须前进。事务记录不入队，其 class
只是阶段标签，不参与跨事务日志排序。

### 2. 禁止零通信延迟

配置校验断言：**所有代理的 `latency_ns ≥ 1`**。零值配置直接拒绝，不静默替换为 1。

约束施加于产生回退 class 队列事件的路径：代理订单使用通信延迟，强平订单使用
`liquidation_latency_ns`。`TRADE_SETTLE`、`MARGIN_CALL` 与 `MARKET_DATA_PUBLISH` 是
父订单事务内的记录，不是队列跳转，不需要额外时间间隔。

- `TRADE_SETTLE`(1) → `MARKET_DATA_PUBLISH`(2)：可同时间戳；
- `MARKET_DATA_PUBLISH`(2) → `AGENT_OBSERVE`(3)：可同时间戳（观察延迟允许为 0）；
- `AGENT_OBSERVE`(3) → `AGENT_DECIDE`(4)：**可同时间戳**，观察到决策的间隔允许为 0。

这一点须写准：观察与决策分成两个 class 的目的是让信息集独立记录（§3.1），不是要求
两者在时间上分开。给它们强加非零间隔是多余约束，且会掩盖规则的真实理由——真正的
规则只有「键严格递增」一条。

在纳秒粒度下，1 ns 已足以表达「几乎无延迟」。速度优势的建模能力不受影响：延迟仍是
显式配置的连续量，做市商与散户的差异照常表达（BENCH-001 已配置 5 ms—50 ms）。

### 3. 因果外键为必备字段

事件新增下列字段，取值为已写入日志的事件标识，不得为悬空引用：

| 事件 | 新增字段 | 指向 |
|---|---|---|
| `AGENT_OBSERVE` | `market_data_event_id` | 本次观察所对应的 `MARKET_DATA_PUBLISH` |
| `AGENT_DECIDE` | `observation_event_id` | 本次决策所依据的 `AGENT_OBSERVE` |
| `AGENT_DECIDE` | `intents[].intent_id` | 本次决策产生的每笔意图的稳定标识 |
| `ORDER_ARRIVAL` | `intent_id` | 产生该订单或撤单的意图 |
| `ORDER_ARRIVAL` | `decision_event_id` | 该意图所属的 `AGENT_DECIDE` |
| `ORDER_ARRIVAL`（`CANCEL`） | `target_order_id` | 被撤销的订单 |
| `TRADE_SETTLE` | `caused_by_event_id` | 触发本次撮合的 `ORDER_ARRIVAL` |
| `SNAPSHOT` | — | 无因果外键，快照是状态观测而非状态转移 |

由此形成可机器验证的路径：

```text
trade_id → caused_by_event_id → taker/maker order_id
        → intent_id → decision_event_id → observation_event_id
        → information_set / market_data_event_id
```

账户变化经 `TRADE_SETTLE` 的 `trade_id` 与账户快照关联，构成 US-3 要求的完整链条。

### 4. 引用完整性作为验收断言（SC-006）

对每次运行的事件日志：

- **遍历全部** `TRADE_SETTLE`（非抽样），沿上表逐跳解析；
- 每一跳的目标事件必须在日志中**唯一存在**，且其 `log_key` **严格小于**引用方；
- 断链、悬空引用或多重匹配即判定运行不合格。

该断言完全在日志内完成，不依赖重放，是 KPI-006 从「展示层可读」升级为「可验证」的
关键。

### 5. 正式研究运行强制 full 信息集

E-001 的 `information_set_mode: digest` 仅用于性能基准（BENCH-001）。**任何用于研究
结论的运行必须使用 `full`**，或产出可独立还原信息集的版本化证据包。

理由：digest 模式下追溯依赖「用当前代码重跑」，而代码版本会变化——一年后无法用当时
的代码复现，KPI-006 的证据能力随时间衰减。研究运行的日志体积是可接受的代价，性能
门槛由性能基准配置单独承载。

### 6. 因果外键不参与事件摘要哈希

`observation_event_id`、`decision_event_id`、`intent_id`、`caused_by_event_id`、
`market_data_event_id` 与 `event_id` 同属实现标识，按 E-002 的既有理由**排除在哈希
之外**。哈希捕捉市场结果的确定性，标识的生成方式属实现细节。引用完整性由 §4 的
独立断言保证，不需要哈希参与。

**`target_order_id` 是例外，必须纳入哈希**（与 event-schema E-002 一致）：撤销哪一
笔订单是外部可观察的市场行为，与已纳入的 `order_id` 同类。若排除，两次运行撤销了
不同订单也会得到相同哈希，KPI-002 会漏报真实的行为差异。

## 备选方案

### 同时间戳语义（对应决策 §1、§2）

| 方案 | 说明 | 评估 |
|---|---|---|
| queue key + log key | 队列调度与事务提交分别排序 | **采纳**。在线执行、日志与重放顺序一致 |
| 同时间戳 microstep / phase 轮次 | 单一键扩为四元组 | 排除。事务边界仍不如双键明确 |
| 允许回到更小 class | 重写「同时间戳优先级」语义 | 排除。等于承认全序键不决定处理顺序，KPI-002 的确定性无从建立 |

零延迟本身也不具建模价值：现实中不存在零延迟通道，而 1 ns 与 0 在任何指标上不可
区分。

### 因果链（对应决策 §3）

| 方案 | 说明 | 评估 |
|---|---|---|
| 显式外键 | 事件携带上游事件标识 | **采纳**。日志自包含，可机器验证 |
| 启发式重建（同代理 + 时间邻近） | 不改 Schema，分析时推断 | 排除。一次决策多笔意图、连续决策时不可靠，且「不可靠」无法被检出 |
| 重放重建 | 需要时用同配置同种子重跑 | 排除为**唯一**手段（仍保留为 digest 模式的补充）。依赖代码版本不变，证据能力随时间衰减 |

## 后果

- **正面**：事件队列和事务日志各自有可断言的单调键；KPI-002 的哈希在实现层有确定的
  输入顺序；KPI-006 可在日志内被机器验证，不依赖重放；撤单与多意图决策的归因不再
  有歧义。
- **负面**：
  - 零延迟配置被禁止，若将来需要「同一时刻的原子多步」行为，须重新评估本 ADR；
  - 每个事件增加 1—3 个标识字段，日志体积上升（估计 5%—10%）；
  - 研究运行强制 `full` 信息集，日志体积显著上升（观察事件是数量最多的一类），须在
    0.1.2 运行前实测并确认存储可行；
  - 引用完整性遍历为 O(事件数)，作为验收步骤而非每次运行的默认开销。
- **后续行动**：见下节文档同步清单；KR-006 的单调性断言与引用完整性检查分别进入
  事件队列实现与因果链验收的范围。
