# 性能基准协议

**创建日期**：2026-07-29　**对应任务**：T000f　**解决问题**：PRD Q-009  
**支撑需求**：KPI-004、NFR-003

## 1. 问题

KPI-004 要求基准仿真在「指定参考硬件」上不超过 10 秒。但个人研究项目通常只有一台
开发机，且会随时间更换——把门槛钉死在某个 CPU 型号上，换机后 KPI 立即失去意义。

本文定义一套**三层判定**，使性能门槛在换机、换 Python 版本后仍可比。

## 2. 三层判定

### 第一层：归一化墙钟时间（主门槛）

直接对比不同机器的耗时没有意义，因此引入校准微基准 **CALIB-001**，测出本机相对
参考机的速度比，再把实测耗时折算回参考机口径：

```text
归一化耗时 = 实测耗时 × (CALIB-001 参考机耗时 / CALIB-001 本机耗时)
```

本机更快时，`CALIB-001 本机耗时` 更小，比值大于 1，实测耗时被放大回参考机口径。

**判定**：`归一化耗时 ≤ 10 秒`（`BENCH-001.yaml` 的 `normalized_wall_seconds_max`）。

**CALIB-001 的负载**必须代表内核的真实瓶颈，而非通用 CPU 跑分：固定次数的
`heapq` 推入/弹出加字典查找——即事件队列与订单簿索引的主要操作。用通用跑分
（如浮点矩阵运算）校准会得到错误的速度比，因为本项目的核心层几乎不做浮点计算。

参考机配置与 CALIB-001 的参考耗时记录在
[`reference-machine.md`](reference-machine.md)。

**该文件规定的计时口径是强制的**——参考机为混合架构 CPU（P 核 / E 核），不绑定
CPU 亲和性、不锁定电源策略时，同一份代码的连续运行结果不可比。

### 第二层：算法回归断言（硬件无关）

归一化仍有噪声（后台负载、缓存状态、温度墙）。因此增加一条**完全确定**的断言：

给定 `BENCH-001.yaml` 的配置与种子，一次运行中订单簿的关键操作次数
（比较、遍历步数）是确定值。将其记录为 `book_operations_golden` 并逐次断言相等。

该计数捕捉真正危险的退化——例如把 O(log n) 的簿查找误写成 O(n) 线性扫描。这类
问题在小规模基准上可能被墙钟噪声完全掩盖，但计数会立即暴露。

golden 值随合法的算法改动而更新，更新须在提交信息中说明原因。

### 第三层：同机相对回归

CI 或本地连续运行时，同一台机器上相对上一个 tagged 版本的归一化耗时退化不得
超过 **20%**。该层用于日常开发，不作为 KPI-004 的正式判定。

## 3. 报告口径

性能结果统一以**事件吞吐量**报告：

```text
events_per_second = max_events / 实测耗时
```

吞吐量与事件总数解耦，便于跨配置比较。墙钟耗时只用于 KPI-004 的门槛判定。

## 4. 校准流程（首次实现后执行）

1. 在参考机上运行 CALIB-001，记录耗时至 `reference-machine.md`；
2. 运行 BENCH-001，记录实测耗时与事件吞吐量；
3. 若实测耗时显著偏离 10 秒（低于 3 秒或高于 30 秒），调整
   `termination.max_events` 使其落在 5—10 秒区间，而**不是**调整门槛值——
   保持门槛为整 10 秒便于记忆，用工作量来适配；
4. 写入 `book_operations_golden`；
5. 上述调整须记录于提交信息，此后 `max_events` 冻结。

`max_events` 的初值 100,000 是估计值，未经实测。

## 5. 运行

实现完成前本目录仅为配置契约。实现后预期入口：

```bash
python -m market_game_sim.bench --config benchmarks/BENCH-001.yaml
python -m market_game_sim.bench --calibrate      # 运行 CALIB-001
```
