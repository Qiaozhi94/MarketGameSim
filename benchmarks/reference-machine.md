# 参考机与运行口径

**创建日期**：2026-07-29　**支撑需求**：PRD / KPI-004；001 / NFR-003  
**关联**：[`README.md`](README.md)

## 1. 参考机

KPI-004 / NFR-003 的参考机为**本地开发机**。服务器集群不参与仿真计算（理由见 §4）。

| 项 | 值 |
|---|---|
| CPU | Intel Core Ultra 9 185H（Meteor Lake-H） |
| 核心构成 | 6 P-core + 8 E-core + 2 LP-E core，共 16 核 22 线程 |
| 基础频率 | 2.3 GHz（睿频显著更高） |
| 内存 | 63.6 GB |
| 操作系统 | Windows 11 Pro |
| Python | 3.11.9 |

CALIB-001 参考耗时：**待首次实现后填写**。

## 2. 计时口径（强制）

该 CPU 为**混合架构**，P 核与 E 核的单线程性能差异显著。计时运行若被调度到 E 核，
耗时可能出现接近一倍的偏差——**不锁定以下四项，KPI-004 的墙钟判定不可信**。

1. **CPU 亲和性**：计时进程绑定到固定的 P 核。Windows 下通过
   `Start-Process -Affinity` 或进程内 `SetProcessAffinityMask` 设置；亲和性掩码
   须记录在结果中。
2. **电源**：必须接入外部电源。电池供电时频率策略不同，结果不可比。
3. **电源计划**：高性能（或"最佳性能"），禁用运行期间的睡眠与降频策略。
4. **Python 版本**：固定为记录版本。跨版本比较须重新测定 CALIB-001 参考耗时。

计时结果取 **5 次运行的中位数**，并同时报告最小值与四分位距。单次运行结果不作为
判定依据。

## 3. 确定性陷阱（影响 KPI-002）

**事件摘要哈希禁止使用 Python 内置 `hash()`。**

CPython 对 `str` 与 `bytes` 的 `hash()` 默认按进程随机加盐（`PYTHONHASHSEED`），
同一份代码、同一配置、同一种子在两次进程中会得到不同结果。若摘要哈希链路中任何
一环使用了内置 `hash()`，KPI-002 将稳定失败，且失败原因极难定位。

要求：

- 摘要哈希一律使用 `hashlib`（建议 `blake2b`），对显式序列化后的字节计算；
- 测试环境显式设置 `PYTHONHASHSEED=0` 作为第二道防线；
- 任何依赖 `set` / `dict` 遍历顺序的逻辑同样禁止（KR-003 已有规定，此处是其在
  哈希链路上的具体表现）。

## 4. 服务器集群的定位

现有六台服务器（详见 opencode `server-manager` skill）单机规格为 2—4 核、
1.6—7.8 GB 内存，合计算力低于本机，**不适合承担仿真计算**。

更重要的是一致性风险：跨机分发运行时，Python 版本、系统库与依赖版本的差异会使
KPI-002 的哈希不一致难以归因——无法区分是代码缺陷还是环境差异。这与宪章第 3 条的
可复现要求直接冲突。

**结论**：

- **计算全部在本机执行。** 16 核对批量实验绰绰有余——M2 全量参数扫描约
  1080 次单线程运行，以 14 并行 worker 计算，即使单次运行 60 秒也可在约 1.3 小时
  内完成。
- **NAS（10.31.0.254，31 GB 内存、大容量存储）作为实验产物归档**：事件日志与
  Parquet 结果推送至 NAS 保存，避免占满本机磁盘。归档不参与计算，无一致性风险。
- 若未来确需分布式运行，须先容器化并固定 Python 与依赖版本，作为独立 ADR 评审。

## 5. 并行口径

- **性能基准（BENCH-001）**：单进程、绑定 P 核，串行执行。并行会污染计时。
- **批量实验**：多进程并行，worker 数建议 12—14（保留余量给系统）。
  各运行之间完全独立，分流 RNG（KR-004）保证并行不影响结果确定性——
  **但须验证：同一种子在串行与并行下必须产生相同的事件摘要哈希。**
